# Platform updates

Runa updates run externally on one developer's checkout using separately supplied owner tooling. After verification, the customer commits and pushes the whole project. Teammates pull that revision and explicitly prepare local dependencies/data; production deploys the same customer revision. Production has no separate platform updater and never acquires an upstream Runa release during deployment.

Customers may modify devcontainer and development/production containers, including adding services. Such customization can complicate updates and requires manual reconciliation of release instructions for Docker/Compose, environment variables and scaffold. Production secrets remain outside Git. The updater reports affected service names and a devcontainer indicator; it requires an explicit continue/abort decision for the exact file plan. Continue applies listed eligible replacements/removals; instruction extensions and customer-owned inputs remain preserved for manual reconciliation. A changed review requires renewed consent.

The updater independently retrieves the original installed and selected stable target releases. Integrity and replacement apply exclusively to delivered src/runa. Modified, missing or unexpected platform files block without repair/force/consent override. It checks application compatibility, preserved dependency locks and actual runtime/database prerequisites. Adapt customer behavior through application/configuration extension points.

Read-only preflight/plan changes no installed source, settings, cache, database data or services. It reports source changes, required platform and module data steps, ordered version paths, transaction/idempotency/recovery declarations, infrastructure review and blockers. Target module metadata is inspected in an isolated read-only PHP container with no Laravel boot, network or private settings mount; migration/upgrade handlers never run to predict effects. Reconcile the release's target dependency composition and locks manually before execution; the updater never overwrites them. Lock consistency does not replace supply-chain policies or release security audits.

Execution records private operation evidence, enables owned maintenance, stops HTTP/application workers, replaces only platform source, installs/builds dependencies and runs forward Runa migrations, required seeds and all supplied Runa-module migrations/upgrades, including disabled modules. Application migrations/seeds/module installers are excluded from this owner update. Stop any custom service that writes data before execution. Automatic customer commit/push, infrastructure replacement and bundled backups are not provided.

If execution fails or is interrupted, preserve the journal/staging and completed data changes. The owner inspects the failed phase before explicit resume of the recorded release. Resume independently verifies source identities and database history; required seeds and module steps with confirmed completion are not replayed. The first failed module step stops later modules and retains its registry fence; transactional steps can resume after rollback, nontransactional steps need declared idempotency or documented operator reconciliation. Existing manual maintenance is preserved. There is no automatic code/data rollback; backups and reviewed recovery are externally managed by the customer.

After a successful update, run application checks, commit the complete reviewed project and distribute that revision through the customer repository. Teammates use runa:dev:initialize for explicit local forward Runa/application data preparation after pulling. Ordinary reopen does not run migrations. Production runa:deploy builds the selected full customer revision and runs required forward Runa migrations/seeds/module upgrades before application migrations and its explicit DatabaseSeeder. Follow the [release reconciliation procedure](../release/platform-reconciliation.md). See [application deployment](deployment.md), [development setup](../development/environment.md) and [database ownership](../architecture/database.md).

## Complete delivered-file review

The external updater compares independently downloaded installed and target customer projections with local delivered files. Plans list exact paths, local/upstream differences, proposed add/update/remove/preserve/manual-reconciliation actions and conflicts, including executable modes/types. Application source/docs, composed dependency inputs, private environment/data/storage/cache and unrelated customer additions remain preserved. Existing instruction extensions and upstream-addition collisions require manual reconciliation. Reports never include environment values.

Read the complete file plan before continuing: consent can replace or remove listed eligible customized files and may leave explicit manual reconciliation work. Consent binds the exact releases and local plan and must be renewed after changes. Protected src/runa mismatches remain an unconditional blocker with no consent override. Read-only modes never mutate the project.
