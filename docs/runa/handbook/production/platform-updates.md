# Platform updates

Runa updates run externally on one developer's checkout using separately supplied owner tooling. After verification, the customer commits and pushes the whole project. Teammates pull that revision and explicitly prepare local dependencies/data; production deploys the same customer revision. Production has no separate platform updater and never acquires an upstream Runa release during deployment.

Customers may modify devcontainer and development/production containers, including adding services. Such customization can complicate updates and requires manual reconciliation of release instructions for Docker/Compose, environment variables and scaffold. Production secrets remain outside Git. The updater reports affected service names and a devcontainer indicator; it requires an explicit continue/abort decision and preserves those customizations. A changed review requires renewed consent.

The updater independently retrieves the original installed and selected stable target releases. Integrity and replacement apply exclusively to delivered src/runa. Modified, missing or unexpected platform files block without repair/force/consent override. It checks application compatibility, preserved dependency locks and actual runtime/database prerequisites. Adapt customer behavior through application/configuration extension points.

Read-only preflight/plan changes no installed source, settings, cache, database data or services. It reports source changes, required platform data steps, infrastructure review and blockers. Reconcile the release's target dependency composition and locks manually before execution; the updater never overwrites them. Lock consistency does not replace supply-chain policies or release security audits.

Execution records private operation evidence, enables owned maintenance, stops HTTP/application workers, replaces only platform source, installs/builds dependencies and runs forward Runa migrations and required seeds. Application migrations/seeds are excluded from this owner update. Stop any custom service that writes data before execution. Automatic customer commit/push, infrastructure replacement and bundled backups are not provided.

If execution fails or is interrupted, preserve the journal/staging and completed data changes. The owner inspects the failed phase before explicit resume of the recorded release. Resume independently verifies source identities and database history; required seeds with confirmed completion are not blindly replayed. Existing manual maintenance is preserved. There is no automatic code/data rollback; backups and reviewed recovery are externally managed by the customer.

After a successful update, run application checks, commit the complete reviewed project and distribute that revision through the customer repository. Teammates use runa:dev:initialize for explicit local forward Runa/application data preparation after pulling. Ordinary reopen does not run migrations. Production runa:deploy builds the selected full customer revision and runs required forward Runa migrations/seeds before application migrations and its explicit DatabaseSeeder. See [application deployment](deployment.md), [development setup](../development/environment.md) and [database ownership](../architecture/database.md).
