# Module framework contracts

## Delivery status and scope

The schema-version-1 manifest validator, deterministic owner-scoped discovery, persistent registry, generation-aware snapshots, local module autoloading, graph-only lifecycle previews, durable atomic administrative transitions, module-owned health observations, effective availability, independent maintenance reasons, PostgreSQL/storage boundaries, availability-aware typed PHP/HTTP adapters, managed database-queue work, classified Artisan/schedule adapters, independent public events, optional integration toggles and typed encrypted settings with controlled reinitialization, versioned trusted management projections and opt-in frontend pages/named slots are delivered. Owner-scoped install/update orchestration, nonmutating target plans and tracked upgrade chains, development generators, independent module version checks and a reusable contract suite are delivered. Managed operations use the declared PHP/HTTP/job/command/schedule/event boundaries; other module entrypoints remain unsupported. Ordinary application PHP/Vue and independent frontends remain supported.

Modules share the existing Laravel application and container. They are trusted local code, not sandboxed plugins or independently downloaded Composer packages. The framework enforces declared boundaries; static checks and PostgreSQL schema conventions cannot sandbox deliberately malicious code.

## Identity and source layout

The public module ID is `<owner>.<code>`, where owner is exactly `runa` or `app`. Code matches `[a-z][a-z0-9]*(?:_[a-z][a-z0-9]*)*` and is at most 58 ASCII bytes, leaving room for PostgreSQL's 63-byte identifier limit. Codes are unique within an owner; `runa.filesystem` and `app.filesystem` may coexist. The ID is a contract key; management records use bigint identity and UUIDv7 public identifiers where externally exposed.

| Item                      | Runa ownership               | Application ownership       |
| ------------------------- | ---------------------------- | --------------------------- |
| Module root               | `src/runa/modules/<code>/`   | `src/app/modules/<code>/`   |
| Domain schema             | `runa_<code>`                | `app_<code>`                |
| Private/public disk owner | `runa`                       | `application`               |
| Disk-relative prefix      | `modules/runa/<code>/`       | `modules/app/<code>/`       |
| PHP prefix                | `Runa\Modules\<PascalCode>\` | `App\Modules\<PascalCode>\` |

Each root contains `module.json`, `backend/`, `resources/`, `routes/`, `database/`, `config/`, `lang/` and `tests/` as needed. Module documentation lives centrally under `docs/app/modules/<code>/` for application modules and `docs/runa/handbook/modules/<code>/` for delivered Runa module guidance; never create a module-local `docs/` directory. Public PHP interfaces/DTOs/events live in `backend/Contracts/`; Actions, models, jobs, providers and other implementation classes live under `backend/`. Frontend code lives in `resources/js/`; migrations and seeders in `database/`. Writable files never live in module source.

Derive PascalCode by capitalizing and joining code segments. Reject case-insensitive PHP prefix collisions, including collisions with ordinary application/platform classes, rather than silently renaming a prefix. The local autoloader derives an explicit prefix-to-`backend/` mapping from the synchronized registry snapshot: broad `App\`/`Runa\` Composer mappings alone do not handle lowercase module roots. No per-module dependency or Composer autoload edit is required. It checks the source manifest hash and canonical owned class path before loading; loading a class does not instantiate descriptors or activate a module.

Source roots, manifest files and referenced files must remain inside the owning real directory without symlink traversal. Reject reserved codes `platform`, `application`, `shared`, `public`, `system`, `reference` and `module_probe`; only `app.reference` is accepted by controlled development discovery. The retired `module_probe` identity is rejected in every context. A module's owner, code and kind cannot be changed in place to reinterpret retained data.

## Manifest schema version 1

`module.json` is a bounded UTF-8 JSON object, at most 64 KiB and depth 16. Reject duplicate JSON keys, unknown fields, unknown schema versions and invalid values before operational providers load. Empty collections are explicit. There are no database-controlled PHP class names, file paths or executable expressions.

| Required field   | Type and meaning                                                                                           |
| ---------------- | ---------------------------------------------------------------------------------------------------------- |
| `schema_version` | Integer literal `1`                                                                                        |
| `id`             | Validated owner/code ID matching the source root                                                           |
| `kind`           | `core` or `optional`; source-owned, never editable in DB                                                   |
| `version`        | Bounded stable `X.Y.Z` module version                                                                      |
| `platform`       | Supported platform version constraint                                                                      |
| `framework_api`  | Supported module-framework public contract version constraint                                              |
| `name`           | Object containing exactly nonempty `pl` and `en` strings                                                   |
| `description`    | Object containing exactly nonempty `pl` and `en` strings                                                   |
| `dependencies`   | Object containing exactly `required` and `optional` maps from full module IDs to version constraints       |
| `providers`      | List of unique owner-local provider class names                                                            |
| `declarations`   | Map of declaration categories to lists of unique owner-local descriptor class names, as specified below    |
| `docs`           | List of unique repository-root-relative Markdown paths in the central owner module documentation directory |
| `tests`          | List of unique module-relative directories within `tests/`                                                 |

Localized names are at most 160 characters, descriptions at most 2000. Collections are bounded to 256 items per category; class names and relative paths to 256 characters. Required/optional dependency maps must be disjoint, cannot reference self, and Runa modules cannot depend on application modules through either map. A required cycle is invalid; optional integration references never become enablement edges.

Version components are decimal integers without leading zeros, at most nine digits each. Version constraints reuse `Runa\Support\VersionCompatibility`: exact or `=`, `>`, `>=`, `<`, `<=`, `^`, `~` against complete stable triples; whitespace is AND and `||` is OR, maximum 256 characters. Wildcards, partial versions, prereleases and build metadata are unsupported in v1 compatibility evaluation and fail explicitly. Do not use the dev-only transitive Composer SemVer package at runtime. Module versions and framework API versions are independent of platform VERSION; the initial framework API contract is `1.0.0` when delivered.

Every category below is required in `declarations`; an unused category is `[]`, except that `lifecycle` always has exactly one descriptor. Its descriptor classes return typed immutable source definitions, not free-form executable manifest payloads. The `health` category has zero or one `HealthPolicy` descriptor; it groups the module’s checks and validated operational overrides. Source descriptors use category-specific interfaces; unsupported descriptor revisions fail validation. The declaration envelope and boundaries are frozen here; each feature point supplies its detailed PHP types and executable validation before it can be used.

| Category       | Source declaration contract                                                                                                |
| -------------- | -------------------------------------------------------------------------------------------------------------------------- |
| `apis`         | Public interface, contract version, owned implementation binding and operation IDs; consumers receive guarded gateways     |
| `health`       | Module-owned check definitions, severity, default mode, timing, operation applicability and allowed operational overrides  |
| `lifecycle`    | Exactly one module-owned transition/work policy descriptor, including explicit stateless/no-work behavior where applicable |
| `settings`     | Typed/localized definitions, defaults, backend validation, sensitivity and application handler                             |
| `integrations` | Target module/public contract, own toggle/default/config and required operations                                           |
| `http`         | Owned `HttpProvider` business endpoints, stable operation IDs and explicit public/permission boundary                      |
| `commands`     | CommandProvider with stable operation ID, diagnostic/operational classification and owned handler/job target               |
| `jobs`         | Job class, stable operation ID and module work-policy reference                                                            |
| `schedules`    | Stable task ID, owned target operation and schedule definition                                                             |
| `events`       | Versioned public event definitions and owned listener/subscriber definitions                                               |
| `frontend`     | Build-time page/component/navigation keys and named route bindings                                                         |
| `slots`        | Host/contribution IDs, props contract version, default priority and local build-time component keys                        |
| `management`   | Declarative actions, permission identifiers and optional safe custom-component keys                                        |
| `upgrades`     | Stable upgrade step IDs, from/to versions, prerequisites, transactional/idempotency and recovery declarations              |

Descriptor identity is `(module_id, category, key)` with nonempty English snake_case keys. Each descriptor exposes integer `schema_version: 1`. Contract versions and required version ranges are separate from descriptor schema revisions. References to other descriptors use these stable keys, never DB-supplied class strings. Class reflection validates namespace, actual source ownership and expected interface before instantiation. Descriptor construction/provider registration must not mutate data, start work or perform external I/O. Providers bind implementation collaborators; adapters register declared entrypoints. Unclassified module entrypoints are contract violations.

## State and dependency contracts

The registry snapshot separates `registered`, `source_present`, administrative `enabled`, `source_version`, `installed_version`, own health and derived availability. Snapshot `generation` changes invalidate cached effective state; persisted settings/health-policy revisions additionally identify their own changes. A module without successfully installed compatible data cannot operate. Discovery never sets installed version merely because source exists and never runs during ordinary request boot.

Own health is `healthy`, `degraded`, `unhealthy` or `unknown`. Effective availability is `available` or `blocked` with independent structured reasons: disabled, missing source, incompatible contract/data, transition/recovery fence, own critical check, required dependency or platform maintenance. Warning observations may degrade an available module. Root causes contain safe codes, module/check IDs, timestamps and dependency paths; no raw exception, secret or business payload.

New Optional registrations are disabled; Core registrations are mandatory. No future Core is registered or required merely because its name is reserved in platform planning. Empty production registry is valid. Missing previously registered Core remains a maintenance reason. Recovery never changes enabled flags; enabling a dependency never restores cascade-disabled dependents.

### Delivered discovery and registry operations

After forward platform migrations, installation/deployment code can call `Runa\Support\Modules\ModuleRegistry::synchronize('runa')` or `synchronize('app')`, or invoke the trusted CLI equivalent:

```sh
php artisan runa:modules:sync runa
php artisan runa:modules:sync app
```

Each call scans exactly one owner and validates all of its manifests before publication. Missing module roots represent an empty inventory; invalid roots, manifests, declaration source paths, ordinary `Modules` namespace collisions and any nested symlink fail the complete operation. `.gitignore` and `.gitkeep` are allowed root metadata files. Source validation checks declaration names and owned files without executing providers or descriptors; each feature's future adapter validates its own descriptor interface/revision before instantiation. Dependency range syntax/direction is validated before publication; graph compatibility and lifecycle cascades are evaluated over the resulting immutable snapshot as described below.

`shared.modules` persists bigint identity, unique UUIDv7 management ID, owner-local/full identity, source-owned kind, registration/source-presence flags, administrative enabled flag, last source version, nullable installed version and validated manifest metadata/hash. `shared.module_registry_state` holds one generation row and the nullable current update source/owner/fingerprint reservation. `shared.module_transitions` records UUIDv7 operation identity, status, affected module IDs and encrypted preparation progress/tokens. All three are platform-owned technical tables, including when the record describes an application module; native application wipes preserve them. Database constraints reject invalid owner/ID/path/version combinations and disabled Core records. No module-domain FK or domain schema is introduced.

Synchronization locks the existing singleton row, validates/discovers trusted local files and atomically publishes the selected owner's metadata plus generation. Optional records start disabled; Core records start enabled. Repeated identical synchronization changes neither timestamps nor generation. Existing enabled flags, public IDs and installed versions survive source updates and disappearance/restoration. Missing records retain their last validated source metadata. A kind change fails instead of reinterpreting retained data. Sync does not migrate module data, infer installed versions or activate modules. Unregister and explicit re-registration preserve retained provenance through the delivered lifecycle adapter.

`ModuleRegistry::snapshot()` returns immutable `RegistrySnapshot`/`ModuleRecord` values ordered by full ID. It checks the persisted generation on each call, reuses unchanged cached records and takes a read lock while rebuilding so records and generation remain consistent. Callers must reacquire a snapshot to observe changes; a retained immutable value describes its original generation. Snapshot reads and normal application/request boot never synchronize or write registration. The module autoloader consults this snapshot only for a module namespace; registry migrations and synchronization must precede use of module classes. It rejects a source hash change pending explicit synchronization. Class loading alone is not an operational API; use the guarded public PHP/HTTP adapters below.

The forward Runa preparation primitive and external updater explicitly invoke the Runa-owned update contract below. Application deployment code explicitly invokes the same contract for app modules; the platform updater never installs them implicitly. The retained development-only `app.reference` example is the only supplied module source; there are no production Core registrations.

Required dependencies form the activation/availability graph. Optional dependencies only constrain an explicitly enabled integration's usable contract; absence or failure cannot disable the independent module. Required and optional references must still respect ownership direction and version grammar. A future Admin-shaped fixture requires Audit, while unrelated fixtures may configure optional Audit integration. No real Auth, Permissions, Audit or Admin implementation is included.

### Delivered dependency graph and lifecycle previews

`Runa\Support\Modules\ModuleGraph` takes a `RegistrySnapshot`, the running platform version and framework API version (default `1.0.0`). Records expose validated required/optional maps and platform/framework constraints from the persisted manifest in the same locked snapshot as flags and generation. Planning reads no source files, executes no descriptors and writes nothing.

```php
$graph = new ModuleGraph($registry->snapshot(), $platformVersion);
$preview = $graph->preview('enable', 'app.documents');
```

`Runa\Contracts\Modules\LifecyclePreview` has schema version 1, intent, target, generation, ordered `affected` IDs, proposed `changes` (`module ID => enabled`) and immutable `GraphBlocker` values. Enable traverses required edges in lexical order and emits dependencies before consumers, once per module. Already enabled modules remain in the affected graph for validation but need no flag change. Disable traverses enabled registered required dependents and emits consumers before dependencies. Disabled consumers and optional edges never join that cascade. Missing source retains its last validated edges for safe disable planning. Enabling a dependency never includes its previously disabled consumers.

Blockers contain only a stable code, complete root-to-failure path and optional expected constraint/actual version. Codes are `not_registered`, `source_missing`, `dependency_version`, `platform_version`, `framework_api_version`, `ownership_direction`, `required_cycle` `core_disable`, `core_unregister`, `disable_before_unregister` and `registered_required_dependent`. Cycle paths include the closing repeated ID. Errors in another disconnected graph do not block the requested preview. Direct Core disable and any cascade containing Core are blocked. A blocked preview may describe proposed changes for diagnostics; it never authorizes their publication.

`optionalBlockers($consumer, $dependency)` inspects one declared optional edge's presence/source/version compatibility without recursive activation, including when optional references form cycles. An undeclared edge returns `optional_not_declared`. These diagnostics do not change the consumer's required graph. Both-side operational availability and integration toggles are checked by ModuleIntegrations; an empty optional blocker list does not establish operational readiness.

The transition publisher constructs a new graph from a fresh snapshot under the registry publication lock and calls `assertCurrent($preview)`. This recomputes and compares the complete DTO, rejecting changed generations, altered cascades and blocked graphs. Calling it on a retained old graph only validates that old generation and cannot certify freshness. The lifecycle publisher adds module-owned policy revisions, installed-data compatibility, preparation readiness and durable ingress fences before flags can change. PHP/HTTP/queue work adapters enforce health and fences; classified command/schedule adapters use managed queue dispatch; event adapters enforce owned subscriptions and optional integration state. `graphReady()` reports graph validity alone; null installed versions do not become installed data through a preview. The graph planner itself executes no transitions. Management HTTP endpoints are not exposed.

### Delivered administrative transitions and retained data

Trusted CLI/application management code resolves `ModuleTransitions` from Laravel. It uses the running platform manifest version; tests may inject a fixture version. `preview('enable'|'disable'|'unregister', $id)` returns an immutable schema-version-1 `AdministrativePreview`: the graph, safe module plans/revisions and stable blockers. `apply($preview)` recomputes the full preview, reserves one operation and returns a schema-version-1 `TransitionResult` with public operation ID, status, optional publication generation and safe per-module reason codes. No token, raw exception or internal row ID appears in the result. An eligible preview does not reserve the operation or certify operational health.

`LifecyclePolicy` schema version 1 is the module's single source-owned lifecycle descriptor. The resolver revalidates manifest ownership/hash and reflects its actual owned file/interface before construction; persisted class names cannot choose executable code. `plan($intent)` is side-effect-free and returns a bounded `LifecyclePlan` revision, blocked flag and safe reason code. The revision must cover every mutable input used by module preparation; framework settings writers serialize revision changes through the registry lock/generation. Descriptor construction must be side-effect-free. Deployment must restart workers when replacing executable module code.

`acceptsDataVersion($installed, $source)` explicitly confirms retained-data compatibility for every required participant during enablement, including already enabled dependencies. A module with migrations must reject null/unmigrated or incompatible data; only an explicitly stateless/no-data module may accept null. Registration and transition hooks never infer that source presence means data installation, run migrations, reset data or overwrite installed provenance. Installation/update adapters will own installed-version publication.

`prepare(TransitionContext $context, ?string $token)` returns bounded `Preparation('ready'|'waiting'|'refused', $opaqueToken, $safeCode)`. Context includes operation/module/intent, original generation and the validated module plan. Repeated polling uses the same operation and private token. Hooks must be idempotent by operation ID and reversible; their transaction/work/checkpoint policy belongs to the module. `compensate($context, $token)` confirms reversal with `true`, or leaves recovery required with `false`/failure. A null token can mean a process died after starting preparation: reconcile by operation ID instead of assuming no work occurred. No global business-work policy is selected by the framework.

Reservation and publication use short transactions under the registry singleton row lock. A PostgreSQL session advisory lock serializes runners across hooks without a long transaction; loss of the runner connection invalidates its execution authority. A partial unique index permits only one unresolved administrative operation. Source synchronization and explicit re-registration refuse unresolved operations. Reservation increments generation and publishes `RegistrySnapshot::fenced` for the entire affected graph, with every previous flag unchanged. PHP/HTTP adapters consume these fences; later queue/work/command adapters must do the same. Class loading alone does not enforce them.

All changed participants must be ready and plans/revisions/data/graph must remain current before one transaction publishes the complete flag cascade and next generation. Waiting returns `pending`, retaining the fence and all flags. `resume($operationId)` polls waiting work; a new process can continue it. Refusal/exception/publication failure compensates every attempted participant in reverse order, including an interrupted or refusing hook. Successful compensation releases the fence with status `refused` or `failed`; ambiguous compensation retains `recovery_required` and can be retried by `resume`. `cancel` requests the same reversible compensation. A process exiting during a hook leaves durable intent and a fence; the next runner compensates instead of replaying ambiguous preparation. Completed operations are idempotently readable/resumable, and post-publication runtime failures never reverse the committed administrative flags. Preparation tokens are encrypted with the Laravel application encrypter, excluded from diagnostics and cleared after successful publication/compensation; preserve normal application-key recovery discipline.

Unregister requires an Optional module already disabled and no registered required dependent, even a disabled dependent. Core and cascades containing Core cannot be disabled; Core cannot be unregistered. Unregister has no module hook because disabled registration removal introduces no business effect. It marks a retained provenance tombstone instead of deleting domain schemas, files, installed versions or configuration. A missing disabled source can be unregistered; an enabled missing module must restore trusted source to perform its module-owned disable preparation safely. Required dependents must first be explicitly unregistered; optional references do not block unregister.

Normal discovery never revives a tombstone. `ModuleRegistry::registerAgain($id)` explicitly validates current owned source, assigns a new public registration ID, defaults Optional to disabled and preserves installed version/provenance. Incompatible retained data blocks enablement through the module policy; it is never reset. Merely restoring a missing registered source preserves its original public ID and administrative flag. Required dependency/source/compatibility checks then determine availability in the health adapter. There is no destructive uninstall.

## Module-owned health policy

Each module supplies its check handlers, critical/warning classification, `on_use`/`scheduled`/`hybrid` defaults, intervals, timeouts, expiry and applicability to public operations. Its definition specifies which operational values administrators may change in DB and their validation bounds. The base has no global business health cadence or inferred policy. Modules without special checks are healthy when source, installed data and required conditions are satisfied.

The framework implements shared meanings: expired critical observations become unknown/blocking; warning failures/staleness remain diagnostic. `on_use` runs applicable checks on each public operation; `hybrid` also schedules them. Fresh cached results cannot replace required per-use checks. Single-flight deduplication can join genuinely overlapping checks but cannot silently skip a later operation's check. A guarded nested call is another public operation under the callee's policy. Pure internal helper calls do not create extra public-operation boundaries. Use controllable clocks and bounded execution, without claiming a generic timeout can safely terminate arbitrary PHP/external effects.

Scheduled diagnostics and explicit recovery checks can run while business work is blocked. Required dependency failures propagate effective blocking and safe root-cause paths. Recovery recalculates availability, not administrative state. Infrastructure protection may reject invalid/unbounded configuration; it must not substitute a global policy for module-owned rules.

### Delivered health services

Declare zero or one source-owned `Runa\Contracts\Modules\HealthPolicy` in `declarations.health`. Its `schemaVersion()` is 1; `definition($overrides)` returns immutable `HealthDefinition`/`HealthCheck` values and rejects every unsupported override. `check($checkId, HealthContext)` returns a boolean, never a raw upstream payload. Definition revisions cover all module-owned decision inputs. An empty health declaration supplies no special checks and no editable health overrides.

`HealthDefinition` selects `on_use`, `scheduled` or `hybrid`. Each named check supplies `critical` or `warning` severity, integer timeout/interval/expiry seconds and an optional list of exact public operation keys (empty means every operation). Structural safety limits are 64 checks, timeout 1–60 seconds with at most 60 seconds of declared check time per module evaluation, interval 1–86400 seconds, expiry at least interval and at most 604800 seconds. These are infrastructure bounds; actual defaults, permitted overrides and cadence belong to the module. The scheduler polls due scheduled/hybrid checks once per minute; sub-minute intervals require an explicit diagnostic invocation for that resolution.

`ModuleHealth::configure($id, $overrides, $expectedGeneration)` is a trusted management contract. It validates against the owned source policy, locks the registry state, refuses stale generations/unresolved transitions, increments the policy revision and generation and clears previous observations atomically. No deployment or flag change occurs. The JSON override document is bounded; it cannot select executable classes. Validated source manifests remain the only descriptor authority.

`ModuleHealth::diagnose($id)` explicitly evaluates all checks, including for a disabled module before enablement; `php artisan runa:modules:health <module-id>` exposes this to trusted CLI callers. With no module argument the command evaluates due checks for enabled source-present scheduled/hybrid modules, including unavailable ones. The technical scheduler runs this recovery command even during maintenance. Missing/invalid source fails closed without loading a database-supplied handler. Enable previews require nonblocking observations for every affected module; a critical unknown needs explicit diagnosis first. Disable/unregister never require healthy business dependencies.

Observations live in `shared.modules.health_observations`; `health_overrides` and `health_revision` are separate from source, installed-data version and administrative flags. Each bounded result contains a policy/source fingerprint, UTC epoch check/expiry instants, a boolean outcome and an engine-selected safe code. Exceptions, messages, credentials and upstream responses are neither persisted nor returned. Every publication advances registry generation under the singleton lock. Policy/source/registration changes discard late results. Expiry is checked against the current clock on every read; effective availability is memoized only inside one evaluation, never cached across time or generations.

PostgreSQL session advisory locks serialize evaluations per module across processes and release on connection death. A competing or recursive per-use evaluation fails closed with `health_busy`; it never substitutes a fresh cache for a required per-use check. Check code runs outside database transactions. Linux `pcntl` interrupts blocking checks, restores the previous signal state, and refuses to replace an already active process alarm. Missing deadline support blocks evaluation. Check handlers are trusted, read-only code and must also honor `HealthContext::deadline` in network/IO clients; the signal boundary is not a sandbox or a guarantee that arbitrary external effects can be cancelled.

`ModuleAvailability::statuses($target, $operation)` resolves one module (or a list of roots) and its required graph once. A null target inspects all records; a null operation reads observations without executing checks. A supplied operation runs applicable on-use/hybrid checks before rejection, permitting recovery. An active transition fence reads cached own-health observations and stops required-graph traversal: refused ingress must not run checks or advance the reserved generation. Explicit diagnostic/scheduled recovery remains independent and can invalidate a stale administrative reservation. Trusted platform checks use `*` to evaluate all check applicability. Returned `ModuleStatus` objects separate own health, enabled/source/registered state and effective availability, with public registration identity, versions, final generation and at most 128 safe root reasons/path segments. Required graph depth is bounded to 128; deeper graphs fail closed. Disabled modules may retain observed own health, but remain unavailable and never execute checks through ordinary operation evaluation. Required failures, cycles, version/data incompatibility and transition fences block; optional dependencies are not traversed. Concurrent policy/flags/fences or evaluated observations changing before completion reject the whole stale result. Technical recovery does not revive administratively disabled dependents.

### Independent platform maintenance

`MaintenanceState::reasons()` composes manual Laravel maintenance, the existing update marker, unavailable registered Core modules and runtime database/registry requirements. No real Core registrations or dummy Auth/Permissions users are supplied. Core checks include all required dependencies and may recover on-use checks before rejecting traffic. The service never calls `up`, clears a marker or changes enabled flags; clearing one owner’s reason leaves the others intact. Detailed reasons are available only to trusted in-process/CLI diagnostics, not an unauthenticated management endpoint.

Ordinary Laravel HTTP traffic fails with a sanitized 503 during effective maintenance; `/api/health` remains liveness and `/api/ready` returns only `ok`/`unavailable` with no-store headers. Both routes remain reachable through Laravel’s manual-maintenance middleware. Laravel queue and ordinary scheduler maintenance checks consume the same effective state. The scheduler pulse and health recovery are explicitly exempt so recovery can continue. Existing external update/deployment process and Nginx fencing remain owned by their update adapters; these Laravel routes do not bypass stopped infrastructure. `MaintenanceState::assertOperational()` supplies the common guard for future operational commands. Public PHP/HTTP adapters compose maintenance with target availability; managed queue work composes the same guard; classified command/schedule adapters use managed queue dispatch; event adapters enforce owned subscriptions and optional integration state. Availability is never authorization.

## Module-owned transition and work policy

The module supplies the decision mechanism for preparation, pending work, running work, checkpoints, cancellation and compensating preparation. The base never guesses a workflow from job names or selects a business policy from a fixed global catalogue. Even a stateless module declares its no-work behavior explicitly.

The shared protocol transports outcomes rather than business decisions:

| Contract                 | Inputs                                                                                                | Output/guarantees                                                                            |
| ------------------------ | ----------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| Transition preview       | Intent, affected graph, registry generation, module policy/settings revisions and active-work summary | Safe reasons, blockers, expected work behavior and policy revision; no side effects          |
| Prepare                  | Operation ID, same validated context, module-owned plan and transition fence                          | `ready`, `waiting` or `refused`, safe reason codes and opaque module-owned preparation token |
| Preparation status       | Operation/token and refreshed work context                                                            | Current readiness/progress; no claim that flags changed                                      |
| Compensate preparation   | Same operation/token                                                                                  | Confirmed compensation or explicit recovery-required outcome                                 |
| Work decision/checkpoint | Operation/work IDs, generation, cancellation intent and module-owned context                          | Module-owned handling decision and safe progress, enforced through the work adapter          |

`ready`, `waiting` and `refused` describe readiness only. They do not enumerate how a module drains, pauses, cancels, completes or reconciles its work. Module-specific plans/tokens stay opaque to the base and are versioned/validated by the module; diagnostics expose only sanitized summaries. A refused module can block the whole requested cascade. A waiting transition reports pending status separately from success and preserves all prior enabled flags.

The framework validates preview revisions, serializes competing transitions, establishes an affected-module ingress fence, invokes each module policy and atomically publishes all enabled flags plus generation only after every required preparation is ready. It uses short DB transactions around durable reservation/publication, never a transaction held across slow module hooks. A restart/retry binds to the same operation and revalidates preparation evidence. Stale previews require a fresh preview.

Before publication, refusal/failure compensates prepared participants and leaves every enabled flag unchanged. Uncertain compensation leaves an explicit recovery fence. After publication, a new runtime failure changes health/availability rather than pretending the administrative transaction rolled back. Hooks must not introduce irreversible business effects. Required data migrations run during installation/update, never as enable/disable hooks.

Ingress fences and generation checks prevent new work from passing a stale cached gateway or starting from a stale queue dispatch. The module decides what already-running work may complete and where it can stop safely. The base records leases/progress and carries cancellation intent; it never kills work midtransaction or interprets a missing lease as proof that external work was reversed. Pending-work treatment and retry bounds are module-provided. Missing/refused/invalid policy never authorizes new work. Diagnostic recovery remains possible. Core cannot be disabled, including through a forged DB flag or cascade.

## Public boundary and management envelopes

Public PHP contracts use immutable DTOs/interfaces under the owning `Contracts` namespace. A declared interface is resolved through a per-operation availability-aware gateway; consumers never receive an unchecked implementation to retain. Operation identity is `(module_id, operation_key)`, shared by HTTP/CLI/job/listener adapters so policy checks do not depend on transport. Ordinary application code may consume this gateway without becoming a module.

| Envelope                 | Required information                                                                                                                                                 |
| ------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Module status            | Schema version, module ID, public management ID, generation, source/installed versions, registration/enabled/source state, own health, availability and safe reasons |
| Lifecycle preview        | Schema version, intent, affected IDs in deterministic order, expected generation/policy revisions, module decisions, active work and blockers                        |
| Transition result        | Operation ID, `pending`/`succeeded`/`refused`/`failed`/`recovery_required`, publication generation if successful, safe per-module status                             |
| Public operation context | Origin/target module, stable operation/correlation ID, generation and optional actor/system context; no invented Auth user                                           |
| Availability rejection   | Stable reason code, target module/operation, safe root causes and retry information where known                                                                      |
| Active work              | Public work ID, owning module/operation, lease observation, module-provided progress/cancellation capability and safe limitations                                    |

Detailed transport DTOs are implemented with their corresponding adapters. They must preserve these meanings and never expose internal relational IDs, raw tokens or sensitive policy context. Availability is not authorization. Management writes stay trusted CLI-only until real Auth/Permissions can authorize them; HTTP diagnostics are restricted, sanitized and read-only. Module HTTP uses `/api/<owner>/<code>/...` and route names `<owner>.<code>.<operation>`; business resource paths follow normal plural/kebab-case conventions.

Public events carry contract version, module ID, stable event/correlation IDs and safe payload; committed-fact delivery happens after commit. Independent subscriber failure never retries the originating action. Critical coordinated operations use explicit calls and documented consistency guarantees. Foreign-module UUID validation through an API does not prevent a later deletion race; owner-side commands/version tokens/reservations are required when the domain needs stronger guarantees. No cross-module FKs, models/relations, SQL or storage traversal.

### Delivered typed PHP gateway

List owned `ApiProvider` descriptor classes in `declarations.apis`. Each returns `ApiDefinition(contract, proxy, implementation, version, operations, schemaVersion: 1)`. The contract is an owned `backend/Contracts/` interface; the final proxy extends `Runa\Support\Modules\Api\GuardedApi` and implements that interface; the concrete implementation implements the same interface. The version is an exact bounded stable `X.Y.Z`, separate from module/source/framework versions. A consumer requests an exact contract version; unsupported versions or duplicate declarations fail closed. Use separate interface identities for simultaneously supported versions.

Map every interface method to an `ApiOperation('resource.read', permission: null)`. Keys are bounded dot-separated lowercase identifiers; the same key identifies the same operation in HTTP and health declarations. Null permission explicitly declares public access; a permission key requires `OperationAuthorizer`. Typed proxy methods forward only to protected `invoke(__FUNCTION__, $arguments)` and verify/carry their declared return types. Constructors/descriptors/proxies must remain side-effect-free. Do not expose implementation objects, bind them as consumer APIs or bypass the proxy from another module.

Ordinary application Actions/services can inject `ModuleApis` and resolve a typed contract without registering themselves as a module:

```php
$lookup = $apis->resolve('app.documents', DocumentLookup::class, '1.0.0');
$exists = $lookup->exists($publicId);
```

This is a developer example, not a delivered Documents module. A contract may extend framework `PublicReferenceLookup`; the resulting guarded proxy works with `PublicReferenceRule`. API unavailability propagates instead of becoming a false missing-reference validation error.

Resolving creates only a proxy and does not authorize execution. Every method call revalidates source descriptors, exact contract version, maintenance, required graph, installed-data compatibility, transition fences and applicable per-use health. Only then is the owned implementation constructed and invoked. Retaining a proxy never retains old availability. Generation is rechecked after authorization and implementation construction; stale state rejects ingress. Descriptor ownership checks include already-loaded classes and actual canonical source files, and container bindings cannot substitute a foreign object.

Parameters/returns use explicit named scalar/array types, module-owned readonly DTOs or enums. Untyped/mixed/object/callback, union/intersection, reference and static methods are unsupported in this v1 boundary. Arrays and readonly DTO properties are inspected recursively at runtime: no mutable object, model, resource, closure or foreign implementation may cross, including nested content. DTO properties must be public initialized values; nesting is bounded to 32 and each array to 10,000 entries. Arrays require documented element types; paginate growing collections. Do not place sensitive values in public contracts.

`OperationContext` schema version 1 contains target module/key, UUIDv7 operation ID, safe correlation ID, accepted generation and optional origin module. Synchronous nested gateways preserve correlation and record the parent module through `OperationScope`; its stack unwinds on success/failure. HTTP roots reuse the validated request ID; ordinary PHP roots generate one. No Auth user/actor is fabricated. This synchronous scope is not a lease or concurrent coroutine context; managed queue work restores this correlation in its own worker scope.

`OperationAuthorizer::allows($context, $permission)` is an application-injectable trusted boundary. The default denies every protected operation. A custom binding must derive identity from trusted context and enforce server-side policy; callers cannot supply a claimed actor or bypass flag. Null permissions are appropriate only for deliberately public business operations. No module-management HTTP writes or mock Auth/Permissions implementation are supplied.

### Delivered HTTP registration and errors

List owned schema-version-1 `HttpProvider` classes in `declarations.http`. They return bounded lists of `HttpEndpoint(method, path, operation, controller)`. Methods are GET (also HEAD), POST, PUT, PATCH or DELETE. Paths are bounded relative plural/kebab-case resource segments with optional required named parameters, such as `entries/{public_id}`; no expressions, arbitrary prefixes, traversal or optional/wildcard parameters. A module may declare at most 128 endpoints and one endpoint per operation key. Use distinct keys for read/write actions.

Uncached routing registers all source-present declarations, including disabled Optional modules, under `/api/<owner>/<code>/...`, with names `<owner>.<code>.<operation>`. No discovery, synchronization, settings write or migration runs on request boot. Registration rejects duplicate names and exact method/path collisions before publishing healthy routes. Laravel route caching preserves the framework dispatcher, middleware and identity defaults. Middleware re-resolves the current source descriptor and compares its path/method/controller/permission to the cached identity; unavailable/stale/removed entries fail closed without invoking old controllers.

A source-missing or stale/invalid descriptor gets a framework-only rejecting fallback scoped to its module URL prefix. It never loads a module controller. This keeps sync, health recovery and independent modules bootable. Cold/unreachable database registration is skipped; effective maintenance handles ordinary HTTP runtime failure. Deployment must synchronize sources before rebuilding the route cache; cached fallback routes remain rejecting until that rebuild. Diagnostics and CLI recovery do not depend on successful operational HTTP descriptor loading.

The framework dispatcher ensures module availability/authorization runs before module controller construction, route binding and Form Request validation. Controllers are plain owned invokable classes with explicit scalar route parameters and Request/FormRequest method parameters; inject services in the constructor. Implicit Eloquent binding and controller middleware are unsupported and rejected, so hidden middleware cannot appear to enforce authorization while being skipped by dispatch. Validate UUIDv7 identifiers in Form Requests and query through owned Actions/Queries. Put permission enforcement in `OperationAuthorizer`, and substantial write validation in Form Requests. Management transitions remain trusted CLI-only. Non-trivial responses use owned `JsonResource` classes with deliberate wrapping; single resources normally set `$wrap = null`, paginated lists follow the normal API contract.

`OperationRejected` exposes stable English code, target/key, safe PHP root causes and nullable retry information. PHP reasons come from bounded availability diagnostics; HTTP returns only `{"error":{"code":"module_unavailable","module":"app.documents","operation":"resource.read"}}` with no-store caching. Source/policy exceptions, relational IDs, health payloads and tokens are never included. Codes include `platform_unavailable`, `module_unavailable`, `availability_changed`, `api_contract_unavailable`, `http_contract_unavailable`, `http_contract_changed`, `operation_not_declared` and `module_forbidden`. Rejection is 503 by default; authorization is 403, missing operations 404, unsupported requested API versions 409. A useful retry interval is not guessed. Normal controller/FormRequest/domain exception handling retains Laravel's existing status/rendering, including 422 validation; the middleware does not catch downstream errors as availability failures.

Availability is an ingress check, not a lock held throughout a business transaction. Already admitted atomic work can finish; a state change after the last check cannot revoke committed effects. Managed queue work adds durable leases and cooperative checkpoints described below. Business consistency still requires owner-side transactions/revisions/reservations. A nested public gateway is another operation and executes its own health policy, including when an HTTP controller explicitly calls its own public API. These boundaries prevent accidental bypass by consumers, not deliberate abuse by trusted PHP code.

### Delivered queue and active-work protocol

Declare source-owned `JobProvider` classes in `declarations.jobs`. Each returns unique schema-version-1 `JobDefinition` entries: operation key, owned `WorkHandler` and `WorkPolicy` classes, maximum attempts (1–100), minimum retry delay (1–86400 seconds), lease (10–3600 seconds), explicit cancellation capability, a safe limitation code and optional permission. Protected operations deny by default through the existing authorizer. Descriptor construction must remain free of I/O/effects. A null permission explicitly allows the job when module/platform admission succeeds; it does not carry or fabricate a user identity.

Dispatch from ordinary application code or another module through:

```php
$id = app(\Runa\Support\Modules\Work\ModuleWork::class)
    ->dispatch('app.example', 'process', ['public_id' => $publicId]);
```

This is an illustrative module identity, not a delivered module. Managed transport currently requires the configured `database` queue, the same named DB connection as the registry and `retry_after` strictly greater than the declared lease. The job timeout is lease minus five seconds; the worker needs normal Laravel PCNTL timeout support. A checkpoint renews the observed lease, not the worker's fixed attempt timeout. Keep atomic units shorter than those limits. Other transports and unmanaged module Bus chains/batches/closures are unsupported; ordinary application jobs retain native Laravel behavior. No Redis/Horizon dependency is added.

For business transactions with per-use health, call `prepareDispatch(module, operation, payload)` before opening the transaction, then invoke its single-use enqueue closure inside the transaction. Admission performs health/authorization outside the atomic business unit; enqueue rechecks the generation under the publication lock. A stale admission rejects the transaction. Direct `dispatch` combines those steps for ordinary callers. The work row and framework `ModuleJob` envelope enqueue in the same database transaction, rolling back together and becoming visible only after commit. Only bounded JSON scalar/array data (64 KiB) is accepted. Laravel encryption protects the stored payload; the queue carries only the work UUIDv7 and fixed timeout, plus `runa_work` diagnostic metadata. No module object is deserialized before admission. Three infrastructure exceptions use five-second backoff before Laravel fails a broken delivery; module decisions and attempt budgets govern ordinary releases. An orphan envelope with no work row executes nothing. Source-owned classes and the stored manifest hash are revalidated; source drift refuses work until owner reconciliation rather than running a new handler against an old payload. Correlation/origin propagate from dispatch to the worker's operation scope and unwind after every attempt.

`WorkPolicy` schema version 1 supplies `pending(WorkStatus, bool $available)` and `checkpoint(WorkStatus)` decisions. Protocol outcomes are `run`, `retry`, `cancel`, `refuse`, each with a safe reason/progress code and optional bounded delay. These are execution controls, not business policy names. Modules implement draining, cancellation, compensation, reconciliation or any other workflow using their own code and idempotency keys. Missing/invalid policy never authorizes work. Retry delays cannot be below the declaration; availability releases and actual starts consume the same durable attempt budget. A module choosing `run` while unavailable or with unresolved pending cancellation is refused. The base never chooses a retry business policy on the module's behalf.

Before a handler is constructed, worker admission rechecks maintenance, effective dependencies/health, authorization, cancellation and registry generation under the same short singleton lock used by lifecycle reservation. A central payload hook rejects direct module jobs, and `JobProcessing` deletes unmanaged namespace-classified payloads before Laravel command deserialization. The framework envelope also validates diagnostic identity. Metadata/namespace checks protect managed contracts, not deliberately malicious trusted PHP, forged raw payloads or a direct call to an owned implementation. Contract checks for other entrypoints follow their own roadmap points.

`shared.module_work` stores bigint internal identity/FK to the retained registry (RESTRICT both ways), UUIDv7 work ID, admitted generation, correlation, bounded encrypted input, attempts, cancellation intent, safe progress and lease evidence. No module-domain FK or schema is created. States are `pending`, `running`, `succeeded`, `cancelled`, `refused`, `failed`, `recovery_required`. Diagnostics expose `WorkStatus` schema version 1, with accepted/current generations, attempts, cancellation intent, observed lease/progress and the module's declared capability/limitation code. Missing source preserves evidence and reports unknown capability. `active(module, limit)` is a bounded oldest-first view (default 100, maximum 1000); failed and expired attempts remain unresolved work. Administrative previews include per-module state counts without mutating work. Obtain complete counts from the preview and individual records by work ID; a bounded list is not proof that no other work exists.

Disable/unregister reservation atomically fences affected ingress and signals existing work before module preparation, preserving all prior enabled flags while waiting. A pending cancelled job consults its module policy without running per-use health that could invalidate its own transition generation. The lifecycle policy can query work and return ready/waiting/refused; only the module decides when the whole cascade is safe. Cancellation intent survives a failed/compensated disable or later enable; pending old work cannot silently resurrect. Never clear it merely because availability recovered.

A running handler receives `WorkContext` with its stable work ID. Call `checkpoint('safe_progress_code')` **outside database transactions**, between atomic units and before the next effect. The module policy sees cancellation and current generation; it may finish an admitted atomic tail, stop safely, refuse or release with bounded delay. A checkpoint stopping the attempt throws framework `WorkStopped`; do not swallow it and continue. Token/state/lease checks prevent old attempts publishing progress/success. `requestCancellation(id)` records cooperative intent only, even when the module declares limited cancellation; it never kills a process or asserts effects were reversed. Already admitted effects may finish between observations, and external systems still require module-owned idempotency/reservations/compensation.

Expired leases project/persist `recovery_required` with `lease_expired` evidence; duplicate delivery never steals or automatically replays a crashed attempt. Handler exceptions become sanitized `failed` evidence, without automatic replay of ambiguous effects or payload/exception logging. Both remain in active-work diagnostics. Trusted `recover(id)` calls the module's pending policy with availability false after external reconciliation: explicit `retry` queues a bounded new delivery, while `cancel`/`refuse` acknowledges a terminal outcome. A `run` decision alone cannot authorize recovery. Old payloads require the same manifest hash and remaining attempt budget; cancellation intent remains. Lease expiry cannot prove an old process or external operation stopped, so reconcile it before authorizing replay. Terminal evidence is retained; there is no automatic work-history purge or public management HTTP endpoint.

## Delivered PostgreSQL boundaries

`ModuleIdentity` derives the schema, qualified table and storage prefix from the stable owner/code ID. Identifiers are validated before SQL construction; the longest Runa schema is exactly 63 bytes. Module schemas use `runa_<code>` and `app_<code>`; ordinary application code retains its conventions outside claimed module namespaces.

Use `Runa\Support\Modules\Data\ModuleSchema($connection, $identity)` in explicit migrations. `create($table, $columns, $exposed = true)` supplies a bigint `GENERATED ALWAYS AS IDENTITY` primary key and, for exposed entities, unique non-null UUIDv7 `public_id` with a database version/variant constraint. Add business columns, `timestampsTz()` and `softDeletesTz()` in the Blueprint callback. Set `exposed: false` for technical/pivot rows without external identity. The generated public-ID index has a bounded identity-derived name even with maximum-length schemas/tables; give other long index/FK names explicit short names.

```php
$identity = new \Runa\Support\Modules\ModuleIdentity('app.orders');
$schema = new \Runa\Support\Modules\Data\ModuleSchema(DB::connection('pgsql'), $identity);
$schema->create('orders', function (\Illuminate\Database\Schema\Blueprint $table): void {
    $table->text('description');
    $table->timestampsTz();
    $table->softDeletesTz();
});
```

Creation and `table($name, $columns)` alterations run transactionally. A registered, source-present identity is required regardless of its enabled flag. Schema claims serialize with a transaction advisory lock. New schemas receive comment `runa.module.v1:<module-id>`; an existing schema without that exact marker is a collision, including an ordinary application schema of the same name. Never adopt it automatically. Comment plus retained registry identity establishes ownership without another technical table. Claims never run on enable/disable or ordinary boot.

Both schema primitives inspect actual PostgreSQL FK metadata before commit. An FK crossing the module boundary, or using anything except `ON DELETE RESTRICT ON UPDATE RESTRICT`, rejects and rolls back the DDL. Same-module FKs use bigint internal IDs. Ordinary application code must also consume public contracts rather than introduce FKs into module schemas. Arbitrary raw SQL remains trusted code subject to the planned contract checks; these adapters are not a SQL sandbox.

`Data\ModuleModel` is the base for exposed domain models. Implement static `moduleId()` and explicit schema-qualified `$table`. It generates UUIDv7 on create, binds routes through `public_id`, hides internal IDs in default serialization and includes soft deletion. Related/through models must use the same base, identity and connection; explicit pivot tables must use the same schema. Open `morphTo` is unsupported because eager loading can instantiate database-selected foreign classes; use explicit owned relations. Custom queries/joins and ordinary models still require boundary review. Non-trivial APIs still use JsonResource rather than raw serialization.

Resolve `Data\ModuleDataPaths` for sorted regular PHP files under current source `database/migrations/` and `database/seeders/`. It revalidates manifest identity/hash, canonical ancestry and every file without executing them or filtering disabled modules. Migration names are `YYYY_MM_DD_HHMMSS_<owner>_<code>_<description>.php`, avoiding shared owner-history collisions. Missing directories mean no files; symlinks, nested directories, foreign names and stale/missing/unregistered sources fail. These are reusable installation inputs: native commands still select the existing application/platform migration roots. Module-aware execution, seeder loading and upgrade journals belong to the install/update point. Do not add request-time migration registration or a second repository.

Native application wipe/fresh preserves claimed Runa-module tables, including disabled, missing and tombstoned registrations; app-module tables remain application-owned. Marker/registry disagreement and unclaimed `runa_` tables block destructive work for inspection. Existing isolated-test-database guards and transactional `DROP TABLE ... RESTRICT` remain mandatory. Wipe retains schemas/claims and registration metadata: explicitly reconcile a domain data reset with retained installed-version provenance before reuse. Disable, missing source and unregister preserve schemas, files, configuration and installed versions; incompatible restoration never resets them.

### Driver-independent storage and public references

Resolve `Storage\ModuleStorage`, then `disk('app.orders', 'private'|'public')`. The factory selects existing owner disks (`application_private/public` or `runa_private/public`); infrastructure configuration can supply a compatible local or remote Flysystem driver. A `ModuleDisk` exposes string/stream reads/writes, exists, copy, move, delete, sorted relative file listing and scoped subdirectory deletion. Every operation prefixes `modules/<owner>/<code>/`. No raw adapter/disk, absolute file path, URL generation or arbitrary per-call driver/options are exposed. Uploads and public delivery policy remain the future Filesystem module's responsibility.

Paths must be canonical relative names. Reject absolute/drive/stream paths, controls, backslashes, percent encodings, query/fragment syntax, empty/dot/parent segments and surrounding segment whitespace. Empty paths only list the module root; root deletion is unavailable. Local roots are checked before adapter construction; all existing ancestors/files are rechecked before each operation, including dangling symlinks. Recursive list/delete rejects symlinks anywhere below the directory. Returned driver listings must remain inside the prefix. Owner disks use direct drivers: indirect scoped/read-through disks and additional local driver prefixes are rejected. Custom local wrappers need explicit boundary support; never disguise them as remote drivers.

These checks prevent accidental traversal and existing symlink escapes. They cannot prevent hostile trusted code/drivers or another process swapping filesystem entries after inspection. Restrict directory writes to trusted application processes; this is not an OS filesystem sandbox. Nonlocal prefix behavior is interface-contract tested without adding a remote-driver dependency; verify the actual deployment driver's credentials, prefix and visibility behavior separately. Low-level data/storage helpers do not enforce operational availability or authorization; later entrypoint adapters own those gates.

Store foreign-module references as UUIDv7 without an FK. `Contracts\Modules\PublicReferenceLookup::exists($publicId)` is implemented by the target module's versioned public API, never a foreign model/query. `Data\PublicReferenceRule` rejects malformed/non-v7 IDs before lookup and passes canonical lowercase UUIDs. Add `required`/nullable validation explicitly. API failure propagates rather than pretending a resource is absent; guarded availability dispatch arrives with the public API gateway point.

Existence validation is a point-in-time check: another transaction can delete/change the target before caller commit. A caller transaction cannot lock foreign rows through this contract. Stronger guarantees require an owner-side command, revision token or explicit reservation/compensation protocol appropriate to the domain. Do not reintroduce FKs/direct reads to hide that race.

## Delivered module Artisan and schedules

Declare `CommandProvider` classes in manifest `declarations.commands`. Each returns schema-version-1 `CommandDefinition(key, classification, target)`. Names derive as `<owner>:<code>:<key>`; collisions fail rather than replace an existing command. Definitions are source-owned, including classification. Disabled modules still register commands. Missing, stale or invalid module declarations are omitted without preventing independent modules or platform recovery commands from booting. Cold setup does not require registry tables. Source changes require synchronization and a fresh Artisan/scheduler process; cached wrappers revalidate current declarations on every invocation.

- `diagnostic`: target implements owned `DiagnosticHandler::diagnose(array): array`. Trusted CLI diagnosis and health recovery remain available while disabled, unhealthy or under maintenance. This is an explicit trusted recovery boundary, never an operational bypass or HTTP management surface. Handlers own secret-safe bounded output and recovery policy.
- `operational`: target is an owned `JobDefinition` key. The command returns `{work_id, status: pending}` after atomic managed enqueue, rather than claiming business completion. `ModuleWork` checks current maintenance, health, enablement, permission and generation at admission and again at worker start. Workers retain module retry/checkpoint/cancellation/reconciliation policies and active-work diagnostics. No raw Artisan handler, shell command, callback or alternate queue can bypass that protocol.

Commands accept `--payload` as a JSON object/array, default `{}`, bounded to 64 KiB and the shared JSON value boundary. They return JSON, exit 0 on successful diagnostic/admission and exit 1 with a fixed safe message for invalid/unavailable execution. A successful admission is not a successful work result. Do not pass secrets on the command line; payload encryption in the managed queue does not protect process arguments or shell history. Long work and business effects belong to declared WorkHandlers; diagnostic handlers must not conceal operational execution.

Declare `ScheduleProvider` classes in `declarations.schedules`. Each returns schema-version-1 `ScheduleDefinition(key, command, expression, overlapMinutes: null)`, targeting a command key of the same module. Framework registration is automatic when Laravel resolves schedules; no per-module global schedule edits are needed. Cron expressions use the installed Laravel cron parser, are bounded to 128 characters and run in UTC. Duplicate task IDs, unknown command keys, unsupported versions and overlap expiry outside 1–1440 minutes fail validation. Schedule names are `module:<module-id>:<task-key>`. Callbacks revalidate the current manifest/task, reacquire classification and invoke the same command adapter; operational admission and later worker execution are separate gates. Availability refusal is a failed scheduled callback with no new queued work; diagnostics remain callable during maintenance. Technical runtime pulse and scheduled health recovery remain unchanged and maintenance-exempt.

Optional `overlapMinutes` applies Laravel's cache mutex to the scheduler callback, including concurrent enqueue attempts. It does not hold a lock for the lifetime of queued business work or deduplicate successive ticks. Modules with long work must choose cadence and implement idempotency/active-work coordination in their owned work policy/handler. Retry bounds and unsafe replay prevention remain in JobDefinition/WorkPolicy; the scheduler adds no retry loop. Ordinary application commands and scheduling retain Laravel behavior. Module PHP is trusted source: these adapters and review contracts are not a sandbox against deliberately unmanaged code.

### Delivered public events and optional integrations

Declare source-owned `EventProvider` classes under `declarations.events`. `events()` returns `EventDefinition(key, version)` facts and `listeners()` returns `ListenerDefinition(key, publisher, event, version, mode, target, integration?)`. Descriptor schema version is 1; event contract versions are positive integers and match exactly. A module has at most 256 events and 256 listeners. Listener keys are stable snake_case identities. Ownership reflection and manifest hash checks apply before constructing descriptors or handlers. Runa subscribers cannot reference application publishers. Providers remain pure declarations; do not register raw Laravel module listeners or serialized module callbacks.

`ModuleEvents::dispatch(module, key, version, payload, eventId?)` validates the declared publisher and current operational availability. It returns immutable `PublicEvent` with UUIDv7 event ID, module/event/version, correlation ID, schema version 1 and bounded public JSON payload (60,000 encoded bytes). Public schema, safe payload selection and independent event SemVer documentation belong to the publisher. Never include internal relational IDs, secrets, models or mutable objects. An existing stable event ID can be supplied by the originating use case; it must always identify the same fact/envelope.

For a database use case, admit before its transaction and register publication inside that transaction:

```php
$publish = app(\Runa\Support\Modules\Events\ModuleEvents::class)
    ->prepare('app.documents', 'created', 1, ['public_id' => $publicId]);
DB::transaction(function () use ($publish): void {
    // Commit the owner's domain write here.
    $publish();
});
```

Publication uses Laravel's callback on the registry/default database connection after the outer commit. A rollback, including a rolled-back nested savepoint, discards the callback. Outside a transaction it delivers immediately. Do not use a transaction on an unrelated connection and assume this callback tracks it. The prepared closure rechecks the admitted generation when invoked. Subscriber, enqueue and logging failures cannot escape post-commit delivery and make the committed origin appear failed. Logs contain safe event/subscriber/listener/correlation identities and reason codes, without payloads or exception messages.

`sync` targets implement owned `EventListener::handle(PublicEvent, deliveryKey)`. Each independent listener receives its own fresh ownership/integration/operational check and operation scope. Failure is logged and the remaining listeners continue. Event/correlation and originating-module identity propagate into nested operations. Sync delivery is not automatically replayed; modules needing replayable processing declare an async subscriber. Critical coordinated operations use the separate fail-closed typed `ModuleApis` contract, with owner-side transactions/revisions/reservations and documented retry/consistency rules. They must not rely on independent subscriber exceptions rolling back an origin.

`async` targets name an owned declared `JobDefinition` key. The corresponding `WorkHandler` receives `PublicEvent::toArray()` as its payload, and `WorkContext::deliveryKey()` supplies the stable subscriber idempotency key. Such jobs are reserved for event dispatch; generic `ModuleWork::dispatch` cannot invoke them without the listener binding. The framework inserts encrypted managed work and its database envelope atomically, retaining the listener identity and a unique SHA-256 delivery key derived from publisher/event/subscriber/listener identities. Repeated delivery of the identical envelope returns the existing work ID in every state, including completed/failed; conflicting envelopes sharing an identity are rejected. Keep this work evidence while duplicate delivery is possible.

Workers re-resolve the exact publisher/event version, subscriber binding, optional integration and current operational availability before claiming work and before handler construction through generation validation. Disabling, maintenance, changed source or a disabled integration cannot authorize a pending listener. Module-owned pending decisions impose retry bounds/delays; cancellation, leases, checkpoints and crash evidence retain the managed work semantics. On a handler failure, use `ModuleWork::recover(workId)` after module-owned reconciliation. An explicitly idempotent subscriber may authorize bounded replay through its WorkPolicy; only that subscriber is queued again, with the same fact, work ID and idempotency key. The originating action and successful independent listeners are never replayed by recovery. Ambiguous crashed work is not blindly retried. External duplicate effects still require the subscriber's own durable deduplication/idempotency or provider key; framework work deduplication does not provide exactly-once business effects.

After-commit publication is an in-process callback, not a durable transactional relay: process loss between origin commit and callback/enqueue can leave a fact undelivered. Enqueued managed work is durable. For a use case requiring stronger delivery guarantees, establish an explicit owner-side coordinated/persisted fact contract before relying on events; never retry the origin just because a subscriber is unavailable.

Declare `IntegrationProvider` classes under `declarations.integrations`, returning up to 128 `IntegrationDefinition(key, target, defaultEnabled, names, defaults)` values and a pure `validConfiguration(key, completeConfig)` validator. Each target must be a declared optional dependency. PL/EN names and non-sensitive JSON defaults/config describe the integration; defaults and every stored configuration are validated by the owner. Configurations are bounded to 8192 encoded bytes each. Secret configuration belongs to the settings/encryption contract, not these public values. Required dependencies, such as the future Admin → Audit edge, remain required graph edges and cannot be weakened by an optional integration toggle. No real Audit module is supplied.

Trusted management code uses `ModuleIntegrations::metadata(module)` and `configure(module, key, enabled, config, expectedGeneration)`. Operational values live in bounded `shared.modules.integration_values`; source sync, disable/unregister and explicit re-registration preserve them. Writes serialize through the registry singleton, reject stale generations/unresolved transitions and publish a new generation. They never enable or disable either module, run business hooks or expose a management HTTP endpoint. Until real authorization exists, callers own the trusted CLI boundary.

Call `requireAvailable(module, key)` at an optional integration operation boundary. It checks the toggle, configuration, declared optional version constraint, both modules' effective availability and platform maintenance. It returns the declared target identity for a guarded public API call. Do not retain an availability result as authorization for a later operation. Event listeners naming `integration` automatically repeat this check at sync invocation, async admission and worker start; the integration must target that event's publisher. Optional absence/incompatibility/unhealth never changes ordinary module enabled state or its unrelated required graph. Cyclic optional references do not recurse through activation. Registered Core failure still causes platform maintenance for these operations.

## Delivered declarative settings

Declare one owned `SettingsProvider` under `declarations.settings` when a module has settings. Its `settings()` returns up to 128 schema-version-1 `SettingDefinition` descriptors with stable key, type, default, PL/EN names and descriptions, backend validation rules/options, `sensitive`, `nullable` and `application` (`immediate` or `reinitialize`). `valid(completeValues)` supplies pure cross-field backend validation; `handler()` names an owned `SettingsHandler`. Construction, validation and defaults must have no effects. Modules without settings need no provider. DB values never select executable classes or validation rules.

Built-in types are strict `string`, `integer`, `decimal`, `boolean`, `enum` and `array`; no coercion occurs. Exact decimal values are canonical decimal strings, never binary floats. Enum `options.choices` is a nonempty list with strict value comparison. Laravel rules enforce additional constraints; integer/decimal min/max use numeric semantics. Defaults and every complete candidate/stored value pass the same type, rule and cross-field checks. JSON values are bounded to 32 KiB with no objects/resources or nonfinite numbers. Register additional trusted `SettingType` implementations through `Settings\SettingTypes::register(key, implementation)` at application bootstrap; built-ins cannot be replaced. This extends backend acceptance; future Admin supplies renderers separately. Infrastructure connections and the encryption key remain Laravel environment/config inputs.

Sensitive definitions require a nullable null default. Supply real secrets through trusted writes, never manifests/defaults/options, source or command arguments. `Settings\ModuleSettings::read(module)` returns registry generation, settings revision and localized definitions with non-sensitive values or sensitive `set` booleans only. It never returns plaintext or ciphertext for sensitive values. `value(module, key)` is an explicit private backend read for trusted owning-module code, including initialization/compensation. Never expose or log its result; operational consumers still require the normal availability gateway. These helpers are not a PHP sandbox against hostile trusted code.

The existing `shared.modules` row stores a Laravel-encrypted JSON value set and monotonic settings revision. Null storage means declared defaults. All values are encrypted, including non-sensitive settings, to prevent mixed plaintext storage and preserve one recoverable snapshot. The externally managed Laravel key/key-rotation configuration is required to read stored values and recovery operations. Wrong/missing keys or corrupt ciphertext fail closed with fixed safe errors; restore the correct external key before recovery. Never regenerate a lost key as a settings repair. Validation/provider exceptions are not chained into diagnostics.

`update(module, patch, expectedRevision, expectedGeneration, actor: null)` accepts only declared keys, retains omitted values and allows explicit nullable clears. It rejects stale revisions/generation and unresolved administrative/settings transitions. The existing transition runner advisory lock, registry row lock and `shared.module_transitions` reservation are reused; no separate journal or audit history store is added. Candidate values, incremented revision and the module fence publish atomically before application. Settings writes preserve enabled/installed versions and invalidate health observations. Even immediate application has a short fence to prevent operations observing unfinished effects. Required dependents inherit blocking through normal availability; already-running work still needs the module's own checkpoint/quiescence policy.

The source-owned handler receives a `SettingsContext` with operation UUIDv7, module, candidate revision, application mode, UTC time, nullable `SettingsActor(kind: actor|system, id)` and safe changes. Non-sensitive keys carry old/new values. Sensitive keys carry only `replaced: true`, including clears. Actual private runtime values are available by explicit backend read, never in hook payloads. The handler owns immediate refresh or reversible reinitialization, active-work decisions and safe refusal. `apply(context)` runs outside DB transactions; only true publishes success. Irreversible effects do not belong here. Deployment must restart workers for executable code changes.

Failed/refused/interrupted application restores the old encrypted values behind the fence, increments the revision again, then invokes idempotent `compensate(context)` with the same operation ID. Only confirmed compensation releases the fence. Restoration, source/schema drift, unexpected direct DB changes or ambiguous compensation retain `recovery_required` and fixed diagnostics without claiming rollback. Source/schema/generation and runner connection are rechecked before completion. `recover(operationId)` conservatively restores/compensates and never replays application. It can retry after the key/source/underlying failure is repaired; terminal recovery calls are idempotent. Lifecycle resume/cancel rejects settings operations; use the settings recovery entrypoint. Terminal operations discard old/candidate encrypted snapshots, retaining only encrypted safe result metadata.

Bind `SettingsObserver::changed(SettingChange)` for future Audit integration. Every changed key carries safe context/change and `succeeded`, `failed` or `recovery_required` outcome. Actor context may be null; no actor model is invented. Independent observer exceptions never reverse settings or log private exception payloads. Delivery is best effort after state publication, with a process-exit gap; consumers deduplicate by operation/key/outcome. There is no audit store, durable audit relay, substitute audit logger, Audit module or management HTTP endpoint. Future Audit owns stronger delivery/history policies.

Trusted CLI: `php artisan runa:modules:settings app.example` prints the redacted read. For a write, pass `--write --revision=<read-revision> --generation=<read-generation>` and pipe a bounded JSON object through standard input: `{"values":{"label":"example"},"actor":{"kind":"system","id":"maintenance"}}`. Omit actor or use null for unknown context. Use a trusted secret source for sensitive values; do not embed them in shell history, arguments or retained files. The CLI never prints its input or private validation/handler errors. `php artisan runa:modules:settings --recover=<operation-uuid>` performs conservative recovery. Reads and confirmed success/recovery exit 0; rejected writes and unresolved recovery exit 1. CLI access is trusted management authorization pending real Auth/Permissions/Admin.

Manifest `docs` references are documentation metadata, not executable paths. Application module paths must stay under `docs/app/modules/<code>/`; Runa module paths stay under `docs/runa/handbook/modules/<code>/`. Discovery validates canonical relative identifiers and owner/code boundaries without opening documents or requiring documentation in runtime/production source. Module tests remain module-relative source paths. Central documentation participates in the normal docs doctor and knowledge corpus.

## Delivered management descriptors

`Runa\Support\Modules\Management\ModuleManagement::read(moduleId)` returns the schema-version-1 `Runa\Contracts\Modules\ModuleManagement` DTO. Trusted CLI `php artisan runa:modules:management app.example` prints the same JSON. It combines the current administrative/effective status and safe root-cause paths, localized identity, required/optional dependency constraints, redacted settings with types/defaults/validation/application/revisions, integration toggle/config metadata, bounded active work and source-owned permission/action/custom-component descriptors. Settings without a provider are null. Sensitive settings expose only set-state; private payloads, lease tokens, executable classes and provider exception text are excluded. Integration configuration is non-sensitive by contract. Missing source preserves status/dependencies/retained work and reports `declaration_source_unavailable`. Known invalid declarations/settings/integrations produce explicit safe diagnostic codes and omit the affected section; metadata errors never change enabled flags. CLI exits 1 for those incomplete views or unknown modules; unavailable business state alone does not fail a complete metadata read.

Declare pure owned `ManagementProvider` classes under `declarations.management`. They return lists of schema-version-1 `ManagementPermission(key, names, descriptions)`, `ManagementAction(key, permission, names, descriptions, renderer: 'action', rendererVersion: 1)` and `ManagementComponent(key, component, permission, renderer: 'panel', rendererVersion: 1)`. Permission/action metadata requires bounded PL/EN text; future Admin selects English. Keys follow the public operation dot/snake_case grammar. Keys must be unique within each collection; each collection is limited to 128 entries. Action/component permission references must resolve to the same module's permission declarations. Permission identity is scoped by the owning module ID. An action and component may share a local key without hiding either permission reference.

Component values are owner-prefixed build registry keys such as `app.example.settings_panel`. They cannot be paths, URLs, imports or executable expressions. The optional frontend build adapter maps these keys to owned local components; consumers check the current manifest hash before rendering. Source metadata cannot load arbitrary code. No component file or fabricated Admin screen is required to declare the future extension contract.

`ManagementRenderers` is a trusted bootstrap compatibility catalogue with exact positive versions, separate `setting`, `action` and `component` kinds. Version 1 defines the six built-in setting types and the `action`/`panel` extension shapes. Additional types require explicit bootstrap registration with `register(kind, key, version)`; built-ins/duplicates cannot be replaced. A custom backend `SettingType` does not implicitly create an Admin renderer: register its setting descriptor compatibility at version 1 separately. Unknown types or unsupported renderer/schema versions produce an incomplete fail-closed metadata view. Catalogue registration describes the renderer contract, not an installed UI implementation.

These are discovery DTOs, not executable action handlers or authorization results. A future authorized adapter binds `(moduleId, actionKey)` to its validated backend use case and resolves identity at its trusted boundary. Existing `OperationAuthorizer::allows(OperationContext, permission)` and `OperationGuard` supply the authorization injection seam; protected operations default to denial. Code presence, descriptors and availability never grant permissions. Preserve generation/revision checks and runtime availability at action execution. This framework provides no real Auth/Permissions/Admin registration, management HTTP endpoint or action executor.

Management reads use cached health evaluation, not explicit diagnostic checks. Active work is ordered by retained work identity, capped at 100 with `workTruncated`; callers can use the existing work API for further inspection. Existing work status reads may expire a stale lease under the work protocol. A view rejects concurrent registry generation changes and asks for retry; work/health may continue changing independently, so it is an observational projection, never write authorization or an atomic business snapshot.

## Delivered frontend pages and named slots

Pure module-owned `FrontendProvider::pages()` declarations return schema-version-1 `FrontendPage` descriptors. `SlotProvider::hosts()` and `contributions()` return `SlotHost` and `SlotContribution`. Register the providers in the manifest's `frontend` and `slots` declaration lists. Component keys and contribution/host IDs are prefixed with the owning module ID; keys never contain paths, URLs or import expressions. Runa contributions cannot depend on application-owned hosts. Duplicate identities, unsupported schemas and invalid owned declarations fail closed for that module without breaking independent modules.

Each page uses a stable snake_case key, PL/EN names, optional area, supported Tabler icon and explicit nullable permission. Its exact entry is `/modules/<owner>/<code>/<page-key>`, named `<module-id>.pages.<page-key>`. Source-present pages register even while disabled. Named compiled routes revalidate current declarations/permission projection on refresh; rebuild the route cache after source synchronization. Unknown paths stay 404. The entry serves the application's built HTML: customers opting in must compose `ModulePage` in their entry; it does not install a shell/router or replace application startup. API-only/custom frontends can ignore the adapter entirely.

`GET /api/modules/frontend` (`api.modules.frontend`) returns an explicitly unwrapped JsonResource with schemaVersion, coherent generation, safe pages/slots and diagnostic codes. It does not return settings, work, registry public IDs, source paths or exception text. Current manifest hashes are public build identity, not secret data. The endpoint evaluates cached health only and performs no registration, health recovery or management write. Disabled pages have hidden navigation; enabled unavailable pages remain disabled diagnostic navigation. Explicit public descriptors use null permission; protected pages/contributions consult the existing request-scoped OperationAuthorizer and deny by default. UI visibility is presentation; all business API operations still require their server guards.

The supplied Vite `moduleComponentsPlugin` exposes `virtual:runa-module-components` only when imported. It scans canonical local `app/modules/<code>/frontend/components/<key>.vue` and corresponding Runa paths deterministically; symlinks and unsafe component filenames are rejected. Keys are `<owner>.<code>.<key>`. Lazy loaders include each manifest's SHA-256 identity. Production mapping excludes development probe/reference names; normal production packaging also excludes their source. Restart Vite or rebuild after manifest/component discovery changes. No database value becomes executable code. Management component descriptors may reference the same registry; a future authorized Admin renderer must still enforce its own permissions and renderer contract.

import loaders from 'virtual:runa-module-components';
import {
  createModuleComponents,
  useModuleFrontend,
  moduleNavigation,
} from '@/runa/modules';
const components = createModuleComponents(loaders);
const frontend = useModuleFrontend();
await frontend.refresh();
// Pass frontend.view to ModulePage/ModuleSlot and moduleNavigation(view, locale)

Use `ModulePage` with a current href, nullable view and built components. It resolves exact same-origin paths (query/hash do not select a different page), verifies availability and matching manifest hash, then mounts the lazy page. Otherwise it renders its `unavailable` slot or localized caller-supplied status text. Unavailable/missing/stale components never start module setup/data requests. Refresh metadata at navigation/recovery and after lifecycle/configuration changes; `useModuleFrontend.refresh()` clears old presentation immediately, aborts previous requests and ignores late results. A snapshot is not a live revocation lock: already admitted operations remain governed by server fences/work policies.

Hosts expose a namespaced stable ID, named props contract, positive version and at most 32 required flat scalar props (`string`, finite `number`, `boolean`). Exact field names/types, contract and version must match; event-like/reserved Vue props are rejected. `ModuleSlot` accepts the host name, current projection, components and exact `values`; it mounts compatible contributions only while both module host and contributor are available, permission is allowed and build identity matches. Ordinary application bootstrap can declare `application.<slot>` hosts with `ModuleFrontend::applicationHost(new SlotHost(...))`; no module registration is required. Native Vue slots remain supported.

Default order is ascending integer priority, then bytewise stable contribution ID. Trusted management can call `ModuleFrontend::order(hostId, contributionIds, expectedGeneration)`; listed IDs precede unlisted defaults. Writes lock the existing registry state and advance its generation. Duplicate/oversized orders and stale generations are rejected. Passing an empty list deliberately resets that host's override. The bounded `shared.module_registry_state.slot_order` JSON object retains missing/disabled/unregistered IDs as inactive entries; source discovery and ordinary availability never prune it. Compatible restoration reuses the order, while explicit incompatible migration/reset owns any pruning. There is no unauthenticated order-write endpoint or fabricated Admin UI.

These two rendering adapters introduce no layout styling or motion; immediate gating/unmounting preserves the availability boundary. Existing shell/component responsive, theme, keyboard and reduced-motion behavior remains authoritative. Contributions own their accessible content and any appropriate motion.

### Delivered structured logging and future Logs read boundary

The default Laravel `stack` writes the same JSON Lines records to container `stderr` and one technical rotating file family, `storage/logs/runa-YYYY-MM-DD.log`. There is no per-module, user or input-derived filename. `LOG_LEVEL` controls both sinks. Monolog retains at most 14 matching daily files when rotation runs; cleanup occurs on writes/close, not from an independent timer. Each file uses `0640` and append locking, shared by PHP-FPM, scheduler and workers. Keep storage and its logs directory restricted to the runtime account/group, outside public mounts. UTC timestamps include microseconds and `Z`; baseline application timezone is UTC. File count and record size are bounded; daily bytes are not capped. Operators must provision/monitor storage and apply an appropriate volume quota or external archival policy for high volume. Container stderr separately uses Compose's 10 MB × 3 rotation.

The JSON envelope contains `datetime`, numeric `level`, `level_name`, `channel`, a bounded static `message`, sanitized `context` and trusted `extra`. `extra.schema_version=1` identifies this read contract. `extra.origin` is `platform`, `application:<stable application ID>`, or a full `runa.<code>` / `app.<code>` module ID. Optional `request_id`, `correlation_id`, `operation_id`, `operation`, `event_id`, `work_id`, `origin_module` and `command` preserve diagnostic identity. Current owner and originating publisher are distinct: a subscriber runs under its own module origin and retains the publisher in `origin_module`. Independent delivery failures remain platform diagnostics with safe publisher/subscriber/event identities in context. The record's context cannot override trusted origin fields.

HTTP establishes a validated request/correlation scope. Ordinary application routes use application identity, platform controller routes use platform origin, and module middleware establishes ownership before constructing controllers or resolving Form Requests. Nested typed API calls replace current operation identity while retaining correlation. Artisan scopes include the registered command name and generated operation/correlation IDs, never arguments/options/stdin. Command names allow 256 bytes to accommodate the full validated module/operation namespace. Module diagnostic commands explicitly scope their owner without becoming operationally authorized. Managed work retains its persisted correlation, work ID and publisher identity across processes; sync and queued event subscribers additionally retain the public event ID. Native application jobs receive a small diagnostic envelope containing only correlation, with application origin derived from their trusted display name. Success/failure queue events and `finally` blocks restore prior scopes before worker reuse. Direct module code outside the managed adapters must explicitly establish a trusted diagnostic scope; logging origin never grants authorization.

For ordinary application services or trusted technical callbacks, inject `Logging\LogContext` and use `run(['origin' => 'application:customer', 'correlation_id' => $safeId], $callback)` with the actual stable application ID. Generated diagnostic identifiers are not credentials. Scopes are synchronous; they are not a concurrent Fiber/request-context implementation. PHP-FPM and the ordinary sequential queue worker are supported. Do not share these mutable scopes between concurrent requests in an alternative runtime.

`SafeLogProcessor` applies before formatting and placeholder expansion on both supplied sinks. Context has at most 32 entries; only approved technical keys retain scalar values, and string values must match the bounded identifier grammar (128 bytes). Unknown keys, nested arrays, objects, request/header/body/settings payloads and exceptions become `[redacted]`; objects are never serialized. Caller-supplied Monolog extra fields are replaced. Messages are capped at 2048 bytes, control characters are removed, common credential assignments/authentication headers/URLs are masked, and exception-bearing records use a constant message to avoid SQL bindings or private exception text. Placeholder expansion is disabled. Emit static English messages and technical identifiers/reason codes; never concatenate user text, secrets, exception messages or sensitive business values into a message or approved identifier field. Pattern masking cannot infer arbitrary secrets embedded in free text. New diagnostic keys require deliberate source review; do not loosen the safe field catalogue to dump payloads. Custom application channels must preserve equivalent filtering/formatting and fixed destinations; on-demand Laravel channels do not inherit the supplied configuration taps automatically.

Future Logs may read the fixed private family and parse the versioned envelope, tolerate absent optional fields/unknown future fields, and filter by origin/correlation/severity. It must bind its own trusted backend read authorization, bounded pagination/search and rotation-aware file access; never accept a user-provided path or expose these files through public storage. No read/search endpoint, UI, Logs module, audit history or substitute Audit logger is delivered here. Logs are diagnostic runtime evidence, not a reliable audit store. They share persistent application storage but are not business backup prerequisites. Customer backup policies may exclude this regenerable family; deliberately retained diagnostic exports require separate access/retention controls. Normal deployment preserves the volume and does not purge unrelated logs, backups or data. After changing logging configuration, rebuild cached configuration and restart long-running workers through the deployment procedure.

## Delivered module installation and versioned upgrades

`ModuleUpdates::plan('runa'|'app')` inventories one source owner without synchronizing registration. It uses a PostgreSQL repeatable-read read-only transaction, validated manifests/paths, platform/framework compatibility, required dependency order (including reverse application compatibility), pure source-owned upgrade preflight and immutable migration history. Enabled flags do not select installation work. Missing registered source, tombstones needing explicit re-registration, downgrades, cycles, incompatible dependencies, changed applied migrations, missing/ambiguous upgrade paths and unsafe retries block before mutation. Optional dependencies do not become installation prerequisites. The plan lists source/installed/target versions, ordered migrations/upgrades, transaction/idempotency/recovery declarations and a whole-module source fingerprint. It never loads migration PHP bodies or constructs/runs upgrade handlers to predict effects. Pending migrations/upgrades and already completed step keys are projected separately.

Declare `UpgradeProvider` classes in `declarations.upgrades`. `upgrades()` returns at most 256 schema-version-1 `UpgradeDefinition` objects; `preflight(?string $installed, string $target)` returns null when ready or a safe blocker code. Providers/constructors and class-file top-level code must be pure. Preflight receives no runtime services; infrastructure is checked by the owning installer/deployment, and module-specific external prerequisites must be reconciled there before invocation. The framework verifies owned handler paths/interfaces through reflection without constructing handlers. Runtime preflight's own database connection is read-only; trusted PHP code is not a sandbox against another connection or arbitrary external effects.

Each definition supplies a stable key, exact nullable `from` (null means first install), exact `to`, owned `UpgradeHandler`, transaction flag, explicit idempotency flag, recovery documentation key and ordered local prerequisite keys. One version edge has one handler, which groups related work. Every installed-to-target hop must have exactly one eligible forward edge, so skipped releases traverse an explicit chain. Prerequisites must be earlier in that chain or belong to a version already installed. Initial installation with no upgrade declarations installs the current schema directly; once data is installed, even a code-only version change needs an explicit no-op edge when no data transformation is required. Preserve published upgrade identities and handlers for supported paths. A recovery key names module documentation, not a framework rollback implementation. Nontransactional steps must supply an explicit recovery key; the transaction_rollback default is rejected for them.

The caller owns its existing exclusive installation/deployment lock, maintenance marker, writer shutdown, operation journal, infrastructure preflight and operator recovery. After platform migrations, application deployment code may explicitly invoke:

```php
$updates = app(\Runa\Support\Modules\Updates\ModuleUpdates::class);
$plan = $updates->plan('app');
// Review/record the plan and enter the deployment's maintenance/writer fence first.
$updates->apply('app', $exactCustomerCommit, function (string $module, string $step) use ($journal): void {
    $journal->recordModuleStep($module, $step); // Illustrative application-owned journal adapter.
});
```

`apply` requires an exact 40-character source commit, no ambient transaction and a nonblocking PostgreSQL session advisory lock. It preflights again, synchronizes exactly the selected owner's source under the existing publication lock, then reserves the same source/owner/fingerprint durably. That reservation fences module ingress and prevents lifecycle/settings publication and ordinary sync/re-registration until completion. It is operational evidence linked to the caller's source journal, not another installation state machine. Resume requires the same owner, source commit and source fingerprint. New Optional registrations remain disabled; existing enabled/settings/integration state is retained.

For each dependency-ordered module, run sorted anonymous Laravel migrations first, then the explicit upgrade chain. Migrations must return `Migration` instances with `up()`, use the registry connection, support PostgreSQL transactions and contain no external effects. Names use `YYYY_MM_DD_HHMMSS_<owner>_<code>_<name>.php`. The framework claims the owned schema and checks RESTRICT/same-module foreign keys; trusted raw SQL still requires review. Design the schema phase to accept all supported historical data versions before data upgrades. Upgrade handlers receive `UpgradeContext` with source operation, module, from/to/key, the connection and `ModuleSchema`. Never use enabled toggles to migrate or seed. Loose module seed files are not discovered/executed; invoke explicit required initialization from an upgrade handler.

`shared.module_update_steps` is a platform-owned bigint-identity/FK ledger with RESTRICT actions. A module/key uniquely identifies a migration or versioned upgrade; its source fingerprint, operation source and running/succeeded evidence survive interruption. Schema work and transactional upgrades commit completion evidence in the same transaction as their effects, without automatic transaction retries. Failed transactional effects roll back and can be explicitly resumed. Nontransactional steps persist running evidence before effects; after failure/crash, replay is allowed only when the handler explicitly promises idempotency. It must deduplicate its own external effects. An ambiguous non-idempotent step blocks until an operator follows the module's documented recovery procedure and reconciles the retained evidence; the framework provides no force/replay/automatic compensation command.

The first failure stops the whole invocation, preserving earlier completion evidence, the prior installed version of the failing module, maintenance and the durable reservation; unrelated later modules do not execute. Installed version is published only after every migration/upgrade for that module succeeds. Completed earlier modules retain their new installed version. A successful invocation clears only its registry reservation; the caller retains ownership of maintenance and health checks. Source rollback cannot reverse committed schema/data/files/external effects. Customer-managed backups and any irreversible-step recovery remain deployment responsibilities. Native application wipes preserve this technical ledger and registry; an intentionally destructive module-domain reset therefore needs explicit reconciliation of retained installed/completion provenance before reinstalling data.

The external updater embeds the module plan and phase in its existing `.runtime/production/in-progress.json` and archives completion evidence there. Its target planner uses an isolated PHP container with read-only target/dependency mounts, no private application settings mount, no Laravel boot and no network. Fixed read-only SQL supplies versions/dependencies/completion metadata; no target migrations or handlers run in preflight. The forward preparation `modules` phase is used by explicit Runa installation, local initialization, external development updates and full customer deployment. It selects only Runa modules. Customers wire app-module invocation/order into their own deployment command or explicit DatabaseSeeder; creating a module never requires a manual central registry entry. No module-management HTTP endpoint, separate package installer, backup engine or new dependency is added.
