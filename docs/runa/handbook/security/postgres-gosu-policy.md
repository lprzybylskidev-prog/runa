# Current PostgreSQL gosu scanner disposition

This narrowly scoped operational policy supports the supplied scanner. It applies only to the exact approved PostgreSQL image, architecture, binary, Go version, finding set and expiry in tools/application/security/postgres-gosu-not-affected.json. Raw reports remain intact. Changed artifacts/findings/evidence or an expired review fail closed; all unrelated findings remain blocking.

## Artifact and method

The OCI index, amd64 manifest, configuration and downloaded file-containing layers were SHA256-verified against the official registry. Only the gosu executable and official entrypoint were extracted for analysis. gosu's SHA256 is `52c8749d0142edd234e9d6bd5237dff2d81e71f43537e2f4f66f75dd4b243dd0`; it exactly matches the upstream gosu 1.19 amd64 release download. `gosu --version` reports `1.19 (go1.24.6 on linux/amd64; gc)`. Go build information reports `CGO_ENABLED=0`, module `github.com/tianon/gosu v1.19.0`, dependencies `github.com/moby/sys/user v0.1.0` and `golang.org/x/sys v0.1.0`.

The [gosu 1.19 source revision](https://github.com/tianon/gosu/tree/6456aaa0f3c854d199d0f037f068eb97515b7513), main program, SetupUser, upstream security policy and wrapper were inspected. Raw `govulncheck v1.9.0 -mode=binary -json <extracted-binary>` was executed, without the upstream wrapper or its exclusions. The analysis tool was built with official checksum-verified Go 1.27.2; binary mode inspected the original embedded Go 1.24.6 build, not the analysis compiler's standard library.

The original 2026-10-17 review used `https://vuln.go.dev`, database last-modified `2026-10-08T22:31:09Z`, and found 65 lower-level version/package events but zero function-level events. That is historical evidence for the exact 25 standard-library records below, not a current whole-binary finding count. A fresh 2026-10-21 unwrapped run additionally reports CVE-2026-111943 / GO-2026-6809 at module level and GO-2026-6686 / CVE-2026-61801 in GetExecUser, GetExecUserPath and ParseGroupFilter. The previous whole-binary zero-function premise no longer holds. Binary mode establishes symbol presence rather than an exploit call graph; retain source/entrypoint and input-trust analysis. Runtime-generated code/plugins are not part of this static gosu program.

Local reproducibility artifacts are under ignored `.runtime/security/gosu-analysis/`: verified OCI evidence, binary/build info, individual Go OSV records, raw govulncheck JSON and summary. These artifacts contain no production credentials. Analysis tools are temporary development tools, not application dependencies or production-image contents.

## Official-entrypoint reachability

The extracted entrypoint invokes `exec gosu postgres "$BASH_SOURCE" "$@"` when initially root. Directory ownership preparation precedes privilege dropping; PostgreSQL then runs as its own user. Runa does not expose a user-supplied gosu user specification or executable through HTTP, SQL or events. There is no interactive TTY/stdin-enabled PostgreSQL service in production Compose.

gosu reads local user/group data, changes supplementary groups/GID/UID, looks up the executable and uses syscall exec. It does not run HTTP, TLS, certificate validation, URL/mail/template/XML/ASN.1 parsers or DNS requests. The `os` package is used, but `os.Root` operations implicated by CVE-2026-39822 are absent from this binary. The Windows-only network condition and CGO-dependent resolver condition also do not match a Linux, CGO-disabled binary. No alternative privilege-drop mechanism is needed to establish these facts.

## Upstream guidance and available update

[gosu SECURITY.md at 1.19](https://github.com/tianon/gosu/blob/1.19/SECURITY.md) directs consumers to assess called APIs using govulncheck rather than infer applicability from the compiler version. Its wrapper has an explicitly explained older setuid-related exclusion; that exclusion was not used in this analysis and does not cover any of these 25 CVEs. The program itself rejects unsupported setuid/setgid installation. Preserve the official normal file mode and entrypoint behavior.

The [latest upstream release](https://github.com/tianon/gosu/releases/latest) checked on the assessment date is still 1.19 (published 2025-09-23). The candidate image uses that exact upstream binary. No corrected newer gosu release replacing this binary was identified. A fix release in the Go database must not be presented as an available fixed PostgreSQL image.

## Current pending-upstream findings and customer decisions

On 2026-10-21, official PostgreSQL 18.6 Alpine 3.24 still resolves to the approved digest and upstream gosu latest remains 1.19. Fresh Trivy 0.76.0 HIGH/CRITICAL scanning reports 26 standard-library findings: the original 25 plus [CVE-2026-111943 / GO-2026-6809](https://pkg.go.dev/vuln/GO-2026-6809). gosu does not invoke certificate verification; the new x509 record is a module-version match in the unwrapped binary analysis. It has not been silently added to the shared 25-finding policy.

The separate [Moby user/group parsing advisory](https://github.com/moby/sys/security/advisories/GHSA-mjcv-p78q-w5fw), fixed in github.com/moby/sys/user 0.4.1, affects functions present in gosu 1.19. This is resource exhaustion when attacker-controlled user/group database content reaches those parsers. The standard entrypoint uses a fixed postgres user; /etc/passwd and /etc/group are root-owned 0644 files, and baseline Compose mounts data and read-only initialization inputs rather than replacing those databases. The database/application user cannot rewrite them. An administrator-controlled image, mount, startup script or user/group customization changes these assumptions and requires fresh assessment. Symbol presence is not proof of a remotely exploitable path, and this record is not covered by the old standard-library disposition.

The Runa owner has accepted a narrowly bound pending-upstream risk for owner development/release verification. This does not ship as automatic customer acceptance: normal customer scans still fail closed on the new finding set. Customers must assess their image, mounts, privileges, initialization scripts and exposure, select a verified corrected upstream image when available, or explicitly record their own scoped decision and review date. Do not reuse an owner's acceptance as a production-readiness claim or disable unrelated scanner findings. No database-volume replacement or removal of privilege dropping is required.
