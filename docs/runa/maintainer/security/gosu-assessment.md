# PostgreSQL Alpine: gosu applicability assessment

Assessment date: 2026-10-17. Scope: Linux/amd64 official `postgres:18.6-alpine3.24`, index digest `sha256:77f585114c32fbca283dc835b0596f4e52b51b4c6662d7810b2f4084f60a1873`. This is a recommendation awaiting a separate user decision. No ignore rule, VEX, risk acceptance, PostgreSQL runtime switch, replacement binary or entrypoint change has been applied.

## Result

The 25 HIGH/CRITICAL reports are genuine published Go standard-library CVEs, but their applicability to this exact gosu executable is a metadata-based false positive. The embedded Go version is correctly detected; vulnerable symbol inclusion/use is not established by that version match. Direct binary govulncheck found zero vulnerable symbols. All 25 requested Go records were present in the analysis; none were excluded. Twenty-four findings were module-only; one reached package-level metadata for `os`, without the vulnerable `os.Root` symbols.

This conclusion is bounded to the exact executable, architecture and intended official-entrypoint invocation. It is not a statement that Go 1.24.6 is generally safe or that unknown gosu vulnerabilities cannot exist.

## Artifact and method

The OCI index, amd64 manifest, configuration and downloaded file-containing layers were SHA256-verified against the official registry. Only the gosu executable and official entrypoint were extracted for analysis. gosu's SHA256 is `52c8749d0142edd234e9d6bd5237dff2d81e71f43537e2f4f66f75dd4b243dd0`; it exactly matches the upstream gosu 1.19 amd64 release download. `gosu --version` reports `1.19 (go1.24.6 on linux/amd64; gc)`. Go build information reports `CGO_ENABLED=0`, module `github.com/tianon/gosu v1.19.0`, dependencies `github.com/moby/sys/user v0.1.0` and `golang.org/x/sys v0.1.0`.

The [gosu 1.19 source revision](https://github.com/tianon/gosu/tree/6456aaa0f3c854d199d0f037f068eb97515b7513), main program, SetupUser, upstream security policy and wrapper were inspected. Raw `govulncheck v1.9.0 -mode=binary -json <extracted-binary>` was executed, without the upstream wrapper or its exclusions. The analysis tool was built with official checksum-verified Go 1.27.2; binary mode inspected the original embedded Go 1.24.6 build, not the analysis compiler's standard library.

The tool used `https://vuln.go.dev`, database last-modified `2026-10-08T22:31:09Z`, symbol-level binary analysis and exit status 0. Its JSON includes 65 lower-level version/package findings across the wider database, but zero function-level findings; those lower-level events must not be described as absent. The requested 25 records were checked individually against the tool's OSV events. Binary mode tests symbol presence rather than producing a source-mode call graph; source/entrypoint review corroborates the absence of relevant functionality. Runtime-generated code/plugins are not part of this static gosu program.

Local reproducibility artifacts are under ignored `.runtime/security/gosu-analysis/`: verified OCI evidence, binary/build info, individual Go OSV records, raw govulncheck JSON and summary. These artifacts contain no production credentials. Analysis tools are temporary development tools, not application dependencies or production-image contents.

## Official-entrypoint reachability

The extracted entrypoint invokes `exec gosu postgres "$BASH_SOURCE" "$@"` when initially root. Directory ownership preparation precedes privilege dropping; PostgreSQL then runs as its own user. Runa does not expose a user-supplied gosu user specification or executable through HTTP, SQL or events. There is no interactive TTY/stdin-enabled PostgreSQL service in production Compose.

gosu reads local user/group data, changes supplementary groups/GID/UID, looks up the executable and uses syscall exec. It does not run HTTP, TLS, certificate validation, URL/mail/template/XML/ASN.1 parsers or DNS requests. The `os` package is used, but `os.Root` operations implicated by CVE-2026-39822 are absent from this binary. The Windows-only network condition and CGO-dependent resolver condition also do not match a Linux, CGO-disabled binary. No alternative privilege-drop mechanism is needed to establish these facts.

## Upstream guidance and available update

[gosu SECURITY.md at 1.19](https://github.com/tianon/gosu/blob/1.19/SECURITY.md) directs consumers to assess called APIs using govulncheck rather than infer applicability from the compiler version. Its wrapper has an explicitly explained older setuid-related exclusion; that exclusion was not used in this analysis and does not cover any of these 25 CVEs. The program itself rejects unsupported setuid/setgid installation. Preserve the official normal file mode and entrypoint behavior.

The [latest upstream release](https://github.com/tianon/gosu/releases/latest) checked on the assessment date is still 1.19 (published 2025-09-23). The candidate image uses that exact upstream binary. No corrected newer gosu release replacing this binary was identified. A fix release in the Go database must not be presented as an available fixed PostgreSQL image.

## Recommendation for the user's three options

1. **Recommended:** retain the official PostgreSQL Alpine image and gosu unchanged; after explicit review/approval, represent only these demonstrated non-applicable findings through a narrow documented VEX/suppression. Bind any future exception to this immutable image digest, architecture, `usr/local/bin/gosu` path, executable SHA256 and the exact 25 CVE identifiers. Reject image/binary drift or new CVEs; expire/review within 30 days and after any image/gosu/tool/database change. Preserve complete unfiltered reports. The result is a false-positive applicability disposition, not permission to ignore genuine reachable HIGH/CRITICAL issues.
2. **Prefer a corrected upstream artifact when one is available and applicable:** review and adopt it deliberately, recheck its binary and remove exceptions that are no longer necessary. No such newer gosu artifact was identified now.
3. **Do not replace gosu on present evidence:** no reachable unpatched vulnerability was demonstrated in this binary. A custom entrypoint or privilege mechanism would create a new security-sensitive maintenance surface without fixing an applicable defect. Reconsider only if future analysis establishes a real reachable issue and an upstream remedy is unavailable.

There is no global severity exemption, no `--ignore-unfixed`, no exception applied to the original Bookworm OS findings and no suppression currently installed.

## User-approved implementation (2026-10-17)

The user subsequently approved the exact-artifact not-affected direction while explicitly preserving upstream gosu/entrypoint. Policy is versioned in `docs/security/postgres-gosu-not-affected.json`. `tools/application/gosu_disposition.py` verifies report completeness, exact image digest/amd64 architecture, the full unchanged 25-CVE set, stdlib version and executable path, then inspects the actual Docker image and checks gosu SHA256/version without starting its entrypoint. New/missing findings, secrets, path/version/image/binary drift or expiry block disposition. Raw reports remain intact; a separate `.disposition.json` binds policy/report hashes and actual image ID. No global ignore or ignore-unfixed flag is used. Review expires 2026-11-16. The policy evidence hash must be refreshed deliberately after assessment-document changes, never implicitly during scanning.

Docker-save archive reports may omit RepoDigests. Docker's containerd image store can expose the manifest/index digest as the inspected ID, while Trivy reports the configuration digest; these are distinct objects ([Docker implementation](https://github.com/moby/moby/blob/master/daemon/containerd/image_inspect.go)). The scanner saves the exact approved digest reference and passes that same archive to the decision before deleting it. The decision hashes the sole configuration referenced by the archive's manifest.json and requires equality with the raw report ImageID, while independently verifying the approved RepoDigest and architecture through Docker inspection. Missing/conflicting digests, configuration mismatch or multiple saved configurations remain blocking. Live gosu checks still execute against the inspected immutable image ID. The raw JSON is not modified; only an in-memory view receives verified digest metadata. Disposition evidence records both inspected and configuration IDs.
