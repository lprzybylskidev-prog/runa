# Owner procedure and historical evidence

Source classification: `docs/runa/handbook/tooling/commands.md`. These owner-only procedures and dated execution records are retained separately from customer guidance. Historical claims keep their original context; current public operations are documented in the handbook.

This file documents the implemented command surface: development lifecycle/profile/setup, passthrough wrappers, seeders, doctor, hooks, knowledge, local quality, security, production lifecycle/deploy tools and frontend/backend checks. RM-2026-001 records their baseline acceptance evidence. Commands still require their documented environment and operational prerequisites; simulation acceptance does not prove real production deployment.

Before a checkout exists, the separately supplied `distribution/bootstrap.py` exception acquires
an exact GitHub release, with public access by default and optional private
credentials. It supports interactive selection, explicit noninteractive inputs,
atomic publication and install-now/postponement. See [bootstrap](../../maintainer/tooling/bootstrap.md)
for host requirements, trust, credential handling and resume instructions.

The [complete inventory and old-to-new map](../../maintainer/tooling/command-migration.md) records each customer/owner command, purpose, side effects and retained orchestration. There are no public action selectors. Use `php artisan list runa` and `php artisan help <exact-command>` for signatures.

Inside the devcontainer: `pnpm run typecheck`, `pnpm run build`, `pnpm run dev` (HMR port 5173 at `/build/`), `python3 tools/maintainer/localization/snapshot.py check`, `php tools/maintainer/testing/localization.php`. `php artisan runa:dev:setup` now includes locked frontend installation/build. Snapshot review/update commands are documented in `docs/runa/maintainer/development/localization.md` and never overwrite local catalogs.

Inside the corresponding worker/scheduler container, `php artisan runa:runtime:health queue|scheduler` verifies its own heartbeat and database access. `php artisan schedule:list` shows the technical pulse. `php tools/maintainer/testing/runtime.php` checks heartbeat/SMTP rejection; development-only `python3 tools/maintainer/testing/services.py` exercises database queue -> SMTP -> Mailpit. Mailpit UI is at `http://localhost:8025`. See `docs/runa/handbook/development/environment.md` for startup order and persistence.

Owner tools `python3 tools/maintainer/test-backend`, `test-frontend` and `test-e2e` use private configurations in `src/runa/tests/`. Only owner Playwright starts the loopback platform fixture harness. Platform tests/harnesses and maintainer runners are excluded from customer delivery. See `docs/runa/maintainer/testing/strategy.md`.

Knowledge commands include automatic first-index initialization and explicit maintenance/retrieval operations. Search supports `--top-k 1..50`, `--explain`, `--document-type`, `--scope`, `--roadmap-id`, `--status` and `--source-path`; quote multiword queries. `--device cpu` forces CPU. Search/eval require a fresh index; doctor reports failures and rebuild explicitly resets the development collection. `python3 tools/maintainer/testing/knowledge.py` runs offline ingestion contracts, `python3 tools/maintainer/testing/knowledge-live.py` checks CPU/CUDA ingestion, and `python3 tools/maintainer/testing/knowledge-retrieval.py` checks real hybrid retrieval in an isolated collection. `php artisan runa:dev:embeddings:set auto|cpu|cuda` selects host GPU policy; apply it with build/up. See `docs/runa/handbook/development/knowledge.md`.

Invoke `php artisan runa:doctor:<area>` for repository, config, templates, maintenance, hooks, frontend, database-migrations, database, seeding, boost, tooling, docs or development. There is no bare global doctor. Production readiness uses `runa:production:self-test`. Owner release/cleanliness checks use `python3 tools/maintainer/check-release` and `check-cleanliness`.

The [inventory](../../maintainer/tooling/command-migration.md) records the operations and scope. Database-migrations retains isolated-test identity protection. Database ownership is isolated as described in [database architecture](../architecture/database.md#platformapplication-source-ownership); final test suite separation remains point 9d.

First installation is owner-controlled standalone delivery; see
[installation](../../maintainer/tooling/installation.md). No Artisan `runa:install` or `runa:project` command is registered. Customer development registers `runa:hook:pre-commit` and `runa:hook:commit-msg`. Installation orchestration stays outside the installation; required operational recovery primitives remain in the platform. Runtime command
`runa:mail:test <recipient>` submits the explicitly requested technical
SMTP check without printing provider errors or secrets.

`php artisan runa:doctor:hooks` invokes installed scripts against a temporary Git repository with safe synthetic fixtures; it never creates fixture commits. Maintenance validator regressions: `python3 tools/maintainer/testing/maintenance.py`. Host/devcontainer argument forwarding contracts: `python3 tools/maintainer/testing/wrappers.py`; these simulate the host context without granting Docker access. Baseline host lifecycle acceptance and its manual editor verification boundary are recorded in closed RM-2026-001.

Lifecycle `up` starts existing images and waits for health; it is not an installer and requires prior migrations/seeding and valid runtime secrets/SMTP configuration. `down` preserves all volumes. `restart`/`logs` accept at most one of the five production services; logs show the last 100 lines. Self-test/isolation, actual-image Trivy scanning, deployment and rollback have baseline host simulation evidence in closed RM-2026-001. Revalidate changed operational surfaces under the applicable roadmap gates. Image build alone cannot establish full production acceptance.

Production env files must be private (mode 600). Simulation mode must match the deploy flag and uses separate Compose resources. All production operations share an exclusive lock. Follow docs/runa/maintainer/production/deployment.md for prerequisites, failure recovery and local acceptance. Backups are customer-managed.

Run quality selections containing host gates from the Docker host; the coordinator delegates application checks to the development container and executes production/scanner gates locally. `show`/`status` work in both contexts. Local operational contracts: `python3 tools/maintainer/testing/operations.py`; production topology/context contracts: `python3 tools/maintainer/testing/production.py`. Neither substitutes for actual host deployment and image-isolation verification.

`python3 tools/maintainer/testing/postgres-alpine.py` is a host-only disposable official PostgreSQL candidate probe. It uses no existing volume, published port or custom entrypoint/gosu; it tests the proposed ICU Polish baseline and removes its uniquely named tmpfs container. It does not adopt that candidate into runtime Compose. See `docs/runa/maintainer/production/postgresql-alpine-assessment.md`.

`python3 tools/maintainer/testing/switch-postgres-icu.py` is the retained one-time host helper for the already delivered selective ICU switch. It records identities/hashes, validates locale/test guards and refuses reused targets/partial state, including the current existing ICU volume. Do not rerun it on the current cluster. The old rollback volume was separately retired by RM-2026-003; the helper performs no cleanup. See `docs/runa/maintainer/production/postgresql-alpine-assessment.md` for current disposition and dated evidence.

Approved PostgreSQL ICU production simulations now use `runa-prod-icu-simulation`, distinct from prior Bookworm simulations. `python3 tools/maintainer/testing/docker-test-inventory.py` emits a read-only resource inventory without environment values for final cleanup review. No cleanup is performed. The security runner retains raw Trivy reports and applies only `docs/runa/maintainer/security/postgres-gosu-not-affected.json` after exact artifact/binary/CVE/evidence/expiry validation; disposition evidence is separate and any drift remains blocking.

The Laravel root is `src/`; repository-root `php artisan` forwards there and framework subprocesses execute from that root. Host wrappers remain repository-relative. `./bin/composer` and `./bin/pnpm` select src automatically; direct container Composer/pnpm/vendor-bin commands run from src. Shared UI/error/translation resources and owner test suites are documented in [Application Architecture](../../maintainer/architecture/application-architecture.md#delivered-source-and-runtime-composition). No repository-root app/config/bootstrap/database/routes/storage links remain.

`php artisan runa:application:check` validates both owner manifests, platform manifest synchronization with VERSION, and application compatibility. Add `--platform-version=0.3.0` to check a stable candidate before operations. It reads source only, exits nonzero for invalid/unsupported/incompatible input and never bumps application version. The supported grammar and manifest contract are in [Application Architecture](../../maintainer/architecture/application-architecture.md#application-identity-and-compatibility). Release validation checks the calculated target with the same evaluator, preserving existing platform release arithmetic. Full updater invocation follows later RM-005 points.

Owner entrypoints are dedicated `tools/maintainer/check-*`, `quality-*`, `test-backend`, `test-frontend`, `test-e2e`, plus `migrate`, `migrate-status`, `migrate-fresh`, `migrate-refresh`, `migrate-reset`, `migrate-rollback`, `wipe`, `make-migration` and `seed`. See the [complete map](../../maintainer/tooling/command-migration.md). They delegate application toolchains into containers; no customer aliases exist. Database operations select only platform paths/history/tables/seeds, retaining test-only destructive guards. Native Artisan database commands select only application ownership. Suite separation remains point 9d.

Customer runa:quality stores results under .runtime/application-quality and uses tools/application/quality.yml and application roadmap metadata under docs/app/roadmaps; basic checks work before a business roadmap is created. Runa release results remain under .runtime/quality; release gates remain in docs/runa/maintainer/quality/gates.yml and run only via the owner quality entrypoint. Owner release checks use python3 tools/maintainer/check-release, not customer runa:doctor. Command splitting is complete; documentation relocation remains point 9e.
