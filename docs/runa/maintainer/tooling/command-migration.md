# Custom command inventory and migration (RM-005 point 9b1)

Every public custom command has one fixed purpose. Action selection is private implementation detail, never a public positional argument. Native Laravel commands and combinations such as `migrate:fresh --seed` are unchanged. The tables cover all existing and planned custom command families; `php artisan list` and each command’s `--help` expose the implemented signatures.

## Customer commands

Development entries are omitted from the production management artifact. Runtime images contain no management executor. The same versioned JSON definitions supply normal/cold Artisan registration and the host transport’s fixed reverse mapping; the executor independently reparses the actual public command. Literal arguments never become executable or shell text.

## Transports and coherent workflows

Retired multi-action bin aliases: `dev`, `doctor`, `quality`, `knowledge`, `security`, `xdebug`, `quality-check`, `production`, `prod`, `seed`. They have no compatibility action dispatch. Use the explicit Artisan commands above. `bin/artisan` remains setup/recovery only; Composer/pnpm/Boost are tool transports. Retained single-purpose recovery aliases are `format`, `lint`, `typecheck`, `analyse`, `test` (backend), `deploy`, and `logs`. `bin/command`, `check`, `operations` only list commands; they execute no action selector.

Versioned Git hooks use separate `tools/application/bin/pre-commit` and `commit-msg` entrypoints. `pre-commit` is the coherent staged-content validation workflow (secret scan, formatting, quick lint, freshness); `commit-msg` validates a message. Their common private engine supplies no public action CLI.

Intentionally retained orchestration: development setup prepares dependencies/environment/assets; startup waits for the application and launches optional AI independently; production build verifies its produced images; production self-test checks deployment readiness; deploy/rollback/install/update preserve their accepted transactions; named quality-roadmap/final commands run the selected dependency graph. Their necessary steps are not unrelated user actions. `format --check`, runner flags, service/profile selection and simulation change the same operation’s behavior, not an additional task. Background quality retains the end-turn/no-poll rule.

Owner quality uses `.runtime/quality`; customer quality uses `.runtime/application-quality`. Owner check/test/quality entrypoints never appear in customer Artisan or delivered source. Raw process engines under `tools/application/executors` are private mechanics. Their defensive action parsers do not define a second public CLI.

Production operation guard: every `runa:production:*` execution, `runa:deploy` and `runa:deploy:rollback` requires the existing installer-selected acquisition mode `prod`. A development, missing or unknown installation mode is rejected before production locks/state, Docker/builds or deployment work. `APP_ENV=production`, production configuration files and `--simulation` do not bypass this restriction. Production simulations use separate production-mode fixture installations. Help, discovery and explicit nonexecuting `--plan` remain available from development. This uses acquisition context, not a first-production history flag or licensing mechanism.

Development operation guard: the entire optional development command catalog (dev lifecycle/profiles, tests, formatting/lint/type/static analysis, doctor/quality, hooks, security checks, Xdebug and knowledge/RAG) is blocked in a prod-mode installation, even if development source was copied there or the caller supplies APP_ENV=local. Existing invalid/unknown acquisition modes also fail closed. PHP checks before local Actions/host dispatch and the independent executor checks before locks, operation-state writes or Docker/tool execution. Production APP_ENV and the configured .env production value also block development tools. Owner development and cold bootstrap remain available before acquisition/environment initialization. Help/discovery and explicit nonexecuting --plan remain available. Production/deploy/host control stay operational; production runtime artifacts still omit development tooling. Native Laravel commands retain their framework safeguards; this guard concerns Runa's optional development catalog.

Owner database operations additionally have fixed standalone entrypoints `tools/maintainer/migrate-status`, `migrate-fresh`, `migrate-refresh`, `migrate-reset`, `migrate-rollback` and `wipe`. Each runs only its named platform operation and retains the isolated-test destructive guard. Customer native Artisan equivalents act only on application paths, history and tables. No owner Artisan aliases, connection/path override or public owner selector exists. Required platform installation seeds are private external orchestration, not a customer command. See [database ownership](../../handbook/architecture/database.md#platformapplication-source-ownership).

## Test ownership

Customer `php artisan test`, `runa:test`, `runa:test:frontend` and `runa:test:e2e` select only `src/app/tests` through the root PHP/Vitest/Playwright configurations. Owner `python3 tools/maintainer/test-backend`, `test-frontend` and `test-e2e` select private configurations under `src/runa/tests`; they have no customer Artisan aliases. The application browser runner targets testing Nginx/PHP-FPM directly, with optional `RUNA_E2E_BASE_URL`; the platform fixture harness belongs only to the owner runner. Both wrappers retain the shared suite lock and child exit codes. Customer acquisition excludes platform tests, harnesses and maintainer runners; shared guarded `src/tests/TestCase.php` remains available.
